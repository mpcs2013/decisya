## Rulings on the six points

### 1. The commitlint step is `continue-on-error`, and the next step enforces its outcome. Does the gate hold in every outcome?

**Yes, the gate holds.** Trace of `ci.yml:80-101`:

| wagoid `outcome` | Mirror result | What the enforcing step does | Job result |
| --- | --- | --- | --- |
| success | success | no drift; `[ "$OUTCOME" = success ]` is true | pass |
| failure | failure | no drift; the last line is false, so exit 1 | **fail** (gate kept) |
| failure | success | drift, `exit 1` | **fail** |
| success | failure (including a `rev-list` error, exit 2, or a missing `python3`) | drift, `exit 1` | fail (fails closed; at worst a false block, which is an availability problem only) |
| cancelled (concurrency or manual) | – | the step's implicit `success()` is false, so it does not run | the job is **cancelled**, so the required check is not green and the merge stays blocked |
| skipped | – | both steps share `if: github.event_name == 'pull_request'`, so they skip together, which happens only on `push` to `main`. Before #59, no commitlint ran on `push` either. If an earlier step failed (for example gitleaks), both skip, but the job has already failed. | unchanged from before #59 |
| any other value | either | the drift branch or the final test fails | fail (fails closed) |

- **No expression injection:** `OUTCOME`, `BASE_SHA` and `HEAD_SHA` reach the script through `env:` and are never inlined into it.
- **Why exit codes are reliable:** the default `bash -e` shell does not abort on the `if python3 …` test. The script's exit status is the status of its last line.
- **Condition:** branch protection must require the **`build-test` job**. The wagoid step's own mark now shows as a warning, not red. The actual failure appears in the next step's log. That is a UX change only.
- **No new capability:** the drift step runs repository Python in a job that already builds PR code with the same token. Fork PRs get a read-only token. A PR can edit `ci.yml` itself. That was true before, and `.github/workflows/**` is in the warning list.

### 2. G4-59-12 covered by the restore audit instead of a separate `--vulnerable` run

**Accepted as an equivalent control, and in part a stricter one.**
- The SHOULD asked for a check "when the warning fires for a NuGet change". A NuGet change alters the restore inputs, so the restore is not a no-op and the audit runs.
- `NuGetAuditMode=all` includes transitive packages. The default `NuGetAuditLevel` (low) makes every NU1901-NU1904 an error under `-warnaserror`. CI's grep blocks only High and Critical, so the hook is stricter.
- Chunk B recorded `NU1903: Warning As Error` as the evidence. CI's separate `Vulnerable packages` step stays in place.

Limits, recorded as G6-59-06 and G6-59-10:
- The audit does not run when the build is NOT RUN (non-HEAD push), and when a dirty tree blocks the push, the build never starts. The docstring's "every package change" overclaims.
- DECISYA0005 does not stop a project from neutralising the audit. It could raise `NuGetAuditLevel`, put NU1901-NU1904 in `NoWarn` or `WarningsNotAsErrors`, or add `NuGetAuditSuppress` items.

### 3. Chunk C committed with `SKIP=gitleaks`, then scanned by hand

**Accepted.**
- The skip was disclosed, it was limited to one commit, and the commit was then scanned with the same pinned binary.
- I reproduced that scan independently: `a941d25` alone and the whole branch range with 8.30.1 `--redact` both gave "no leaks found".
- Two more scans follow: the new pre-push gitleaks hook and CI's `gitleaks-action` scan this commit again before merge.
- Process rule for the future: `SKIP=gitleaks` is acceptable only when a same-version scan of that commit is recorded before the push. G7 should carry a one-line disclosure.

### 4. The prepush.py design

**Sound, and it meets G4-59-05 and 06.**
- **Range:** `merge-base(origin/main, to_ref)..to_ref` is a superset of the commits that are new to the remote. That is conservative: every commit on the branch is linted and warned about, not only the newest ones.
- **Stale `origin/main`:** a stale ref only widens the range. A missing one fails closed with exit 2.
- **Branch deletion:** handled. pre-commit itself skips deletions too.
- **Build:** it runs only when `to_sha == HEAD` and no tracked changes exist, which is exactly P-03's mitigation. A non-HEAD push says "NOT RUN", so there is no false pass.
- **gitleaks pre-push hook:** it reuses the pinned repository and binary, with `--redact` and no report file.
  - Without `--log-opts`, `gitleaks git` scans `--all` refs, which covers the pushed commits and more (stash, other local branches).
  - It picks up `.gitleaks.toml` from the repository root, because pre-commit runs hooks from there.
  - Scanning more than the pushed range is stricter than G4-59-06 asked, and acceptable.

Gaps:
- **G6-59-01:** the tracked-changes check applies only on the dotnet path. The `.claude` lint and unit tests always run on the working tree. They also run on a non-HEAD push without a "NOT RUN".
- **G6-59-02:** pre-commit hands the hook only the first pushed ref.
- **G6-59-07:** scanning all refs costs more time as the history grows.
- **G6-59-08:** the unit tests that pre-push runs create git repositories using the inherited `GIT_*` environment.

### 5. The Directory.Build.targets policy target (DECISYA0001-5)

**Placement and `BeforeTargets` are correct.**
- `Directory.Build.targets` is imported after the project body. Evaluation finishes before any target executes, so the checks see the final property and item values whatever the order inside the project.
- `CollectPackageReferences;CollectPackageDownloads` are in the restore graph walk. The probes show every DECISYA code firing at restore, before NuGet downloads anything and before any package `build/` targets are imported.

**A project can still skip it.** Each route is visible in the diff, and most trigger the pre-push warning. CI builds whatever the PR contains, so this is a drift guard and not a boundary. The control is review, so the rating is Low (G6-59-05):
- `ImportDirectoryBuildTargets=false` can also be set in an imported `.props`/`.targets` file, in `Directory.Build.rsp` or `Directory.Solution.props`, or through an environment variable on the host. The repository test scans only `*.*proj`. Accepting a test here instead of a build check is correct, because a build cannot check its own import. The test just needs a wider scope.
- A nested `Directory.Build.targets` (or `Directory.Packages.props`) shadows the root one for its subtree.
- The target can be redefined (the last definition wins). A project can do this with an explicit `<Import Project="Sdk.targets" Sdk="…"/>` followed by `<Target Name="DecisyaCentralPackagePolicy"/>`, or through `CustomAfterMicrosoftCommonTargets`.
- `GlobalPackageReference` is named in P-07 but has neither a check nor a probe.
- To verify: static-graph restore (`RestoreUseStaticGraphEvaluation=true`) and VS 2026's nomination-based restore may not execute `CollectPackageReferences`. The target file's comment claims VS 2026 coverage, but that was not probed.
- `ImportDirectoryPackagesProps=false` is covered: DECISYA0002 and 0003 fire, because the properties become empty.

### 6. Dependabot's `pre-commit` ecosystem on this public repository

**Accepted.**
- The ecosystem is supported for public repositories, and G4 checked the documentation.
- The only remote hook repository is gitleaks. A bump fails `test_gitleaks_parity.py` until `ci.yml` is bumped in the same PR, which is the intended coupling.
- On a public repository, Dependabot PRs run CI with a read-only `GITHUB_TOKEN` and no Actions secrets. Nothing runs on the host until Marco checks the branch out, and he reads `git diff` first (the runbook's rule).

Notes (G6-59-09):
- `rev:` points at a mutable tag, and pre-commit builds gitleaks from source at that tag.
- There is no `cooldown` on the ecosystem. A freshly published malicious tag would therefore arrive as a PR within a week.
- If the repository ever becomes private, the ecosystem stops working. The comment next to the pin already says to bump both files by hand.
