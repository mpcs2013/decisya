## Verdict

**PASS-WITH-NOTES.** Every G4-32 requirement is met, except G4-32-06, which is met apart from one missing XML-doc sentence (N32-02). The library side of T-01 to T-14 is implemented as G3 specified. No finding is High.

There is one **Medium**, N32-01. The public `static bool TryParse(string?, out TenantId)` is exactly the method shape that ASP.NET Core minimal APIs and MVC (.NET 7 and later) use to bind a type from a route, query string or header. So T-11's premise, "no `IParsable`, therefore not route-bindable", doesn't hold. Nothing binds `TenantId` today, which is why this is Medium and not High. It must be settled before #20 adds the first endpoint. Marco decides which fix; the options are under N32-01.

## Informational (no action in #32)

- **I-1.** Serialising a `Result` or `Result<T>` with System.Text.Json always throws, because one getter (`Error` on a success, `Value` on a failure) throws. This fails closed: neither `Value` nor `Message` can leak onto the wire. It is consistent with the "not a wire type" remark (`ResultOfT.cs:12-14`).
- **I-2.** Logging a whole `Result` object: the #15 masking processor catches the throwing getter, masks that member and increments the `getter` masking-error metric (`SensitiveDataMaskingProcessor.cs:482-490`). That's safe, but it adds noise to a security metric. #20 should log `Error.Code` and `Error.Category`, not the `Result`.
- **I-3.** `Result.Success(default(TenantId))` is accepted. `ArgumentNullException.ThrowIfNull` boxes the struct, which is never null. T-04 already lists this path; `Value` throws downstream. No change.
- **I-4.** A canonical GUID whose characters are all `\u`-escaped in JSON (216 raw bytes) is rejected by the 128-byte cap. That is a fail-closed false rejection, and acceptable. Partly escaped input is unescaped by `GetString()` and then goes through the shape check, so `0x…` is rejected as `0x…`.
- **I-5.** Using `TenantId` as a JSON dictionary key isn't supported: the converter doesn't override `ReadAsPropertyName` or `WriteAsPropertyName`, so STJ throws `NotSupportedException`. That fails closed.
- **I-6.** `DomainError` can't be deserialized, because it has only a private constructor. A payload therefore can't create a `DomainError` that skips code validation.

## Do the reflection tests pin the public surface?

- **G4-32-12 (`TenantIdLoggingTests.cs:489-502`): yes, for what matters.** `BeEquivalentTo` on the name and type pairs fails on any added, removed or retyped public instance property. It doesn't pin fields or methods. That is enough, because the masking analyzer only looks at public instance properties (`SensitiveTypeAnalyzer.cs:219`).
- **G4-32-05 (`TenantIdFormatExceptionTests.cs:411-418`): partly.** It catches a new declared public property, but not a new constructor that takes the input. See N32-05(e).
- **G4-32-07 (`TenantIdTests.cs:145-170`): no, for the binding threat.** It misses the static `TryParse` binding convention (N32-01), a minimal-API `BindAsync`, and conversions from `Guid?` or `ReadOnlySpan<char>`.
- **G4-32-11 (`TenantIdTests.cs:188-200`): partly.** It catches new properties and method return types of `DateTime`, `DateTimeOffset` or NodaTime types. It misses nullable wrappers, `out` parameters and numeric timestamps. See N32-05(f).
- **No bool conversion (`SharedKernelBoundaryTests.cs:89-111`): yes.** Any `op_True`, `op_False`, or conversion that returns `bool` fails it.

## Ruling on test-engineer's note (no `[Trait("Category", …)]` on the new test classes)

**Accepted, no security impact.** CI runs the unit lane as `--filter-not-trait "Category=Integration"` (plus `E2E` and `AppHost`) (`.github/workflows/ci.yml:128`). So an untagged class runs in the unit lane, and every canary and reflection test in this diff runs on every push. A missing tag can't silently skip a security test. The failure mode is the reverse: an untagged test that needs Docker would fail loudly in the unit lane.

The note says this matches the existing SharedKernel tests. That's true for most of them: the `Money/`, `Time/`, `Architecture/` and `BannedApi/` classes on `main` have no trait. `RepoPathsTests` has `[Trait("Category", "Unit")]`, though. `.claude/agents/test-engineer.md:17` says every test class carries a Category trait, so the project is inconsistent with its own convention. That is a tooling or consistency matter, not a security one. It should be settled in its own issue, either by tagging all SharedKernel test classes or by relaxing the agent rule. #32 doesn't need to act on it.
