## Checks requested by the orchestrator

- **ADR-0012 as implemented.** The `None` precondition comes first in all three handlers, ahead of `ArgumentNullException.ThrowIfNull`, and the refusal logs only the command name and the `Kind`. The context is created only after validation, is scoped with `await using` to `ExecuteAsync`, and is disposed before the result returns. The handlers inject `DbContextOptions<EntitlementsDbContext>` and never the DI context (a test pins this).
- **Generic `ProvisionModuleRoleAsync`.** It has two call sites, `MigrationRunner.RunAsync`, which passes `TenancyModule.DatabaseRole` and `Schema`, and `EntitlementsModule.DatabaseRole` and `Schema`. All four are `const string`, and neither role nor schema is read from configuration. Identifiers go through `QuoteIdentifier`. The verifier is bound through `format('%I … %L')`. The #21 statement set is unchanged: explicit DML grants, never `ALL`, and the history-table revoke. Each module's grants run after its own `MigrateAsync`.
- **Second password.** `ValidatePassword` applies the same `\A[A-Za-z0-9]{32,}\z` to both passwords. It runs before any options builder or connection, and tenancy is checked first. The error names only `Migrator:EntitlementsRolePassword`. `MigrationRunnerValidationTests` covers missing, 31-character, quote and trailing-newline values for the new key, on an unreachable host, and checks that the message never contains the value. The password reaches Postgres only as a SCRAM verifier. `MigratorLogTests` extends the structural "no logger factory" proof to `EntitlementsDbContextOptions`. That proof is #21's accepted substitute for a full-run log capture.
- **AppHost connection strings.** `entitlements-db-password` is `secret: true`, `persist: true`, `MinLength = 32`, `Special = false`. The migrator gets it only as `Migrator__EntitlementsRolePassword` and has no `ConnectionStrings__entitlements`. The API gets exactly `ConnectionStrings__tenancy` (`Username=decisya_tenancy`) and `ConnectionStrings__entitlements` (`Username=decisya_entitlements`), both built with `ReferenceExpression`, with no `Migrator__*` key and no owner string. This is pinned statically (`AppHostConfigurationTests`) and on a running AppHost (`TenancyMigratorResourceTests`, which extracts only the `Username=` segment, so a failure cannot print the password).
- **Test-side serialization of the migrator tests.** The collection (`DisableParallelization = true`) covers the two classes that call `RunAsync` against the shared PostgresFixture cluster: `MigrationRunnerIntegrationTests` and `EntitlementsRoleIntegrationTests`. The other `RunAsync` callers fail validation before connecting. No other test assembly creates roles, and no fixture uses container reuse. It hides no product bug that matters with a single migrator:
  - The AppHost declares one `decisya-migrator` resource, and the API uses `WaitForCompletion`.
  - Inside one `RunAsync` the two modules run one after the other.
  - The race needs two concurrent migrators on one cluster. Its outcome is a failed migrator (23505 on `pg_authid_rolname_index` or XX000), which fails closed. It cannot widen a grant, because every statement grants only the fixed DML set to the fixed role.
  - The hardening is already in #83.
- **Other checks.** `Decisya.Api.csproj` adds only the module ProjectReference and no package. The Contracts assembly exposes no `TenantId` or `TenantResolution` (a test pins this). `deploy/sql/entitlements` is DDL only, with no role or secret. The API test placeholder string is `Host=db.invalid…Password=placeholder`. `dotnet list package --vulnerable --include-transitive` reports none for `Decisya.Modules.Entitlements`, `Decisya.Api` and `Decisya.Infrastructure.Migrator`.
