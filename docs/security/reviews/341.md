## Residual risks for Marco (ADR-0027 and ADR-0013 amendment 1)

**R-L-FORGE (ADR-0013 amendment 1): forged audit rows written as `decisya_ledger`.**
- What prevents it:
  - EF-only data access in Ledger, with raw SQL banned by `RawAdoNetRule` and `CrossTenantQueryRule` (static, at build).
  - The writer's shape and ambient checks for every append that goes through `IAuditWriter`. These have no test yet (G6-341-01).
  - The family rule. It exists only as ADR text until G6-341-04 lands.
  - The database checks limit any row, forged or not, to a well-formed shape: action set, subject exactly for ledger actions, feature key exactly for overrides, non-blank actor, trace-id format.
  - `decisya_ledger` holds `INSERT` only on `audit.audit_records`. It cannot read, update, delete or truncate there, so it can neither change nor hide existing rows.
- What only detects it:
  - Every genuine row has a matching request: the `Ledger: <operation> ok, account_id <id>` log line and a trace with the row's `trace_id`.
  - A reconciliation that joins audit rows with traces or logs would expose forged rows. No such job or alert exists today.
- Where nothing contains it:
  - Code running as `decisya_ledger` through an injection, a future raw-SQL bypass, or a leaked `ledger_db` password can insert well-formed rows with any `tenant_id` and any `actor_user_id`. The audit table has no row-level security: the tenant filter is EF-side only.
  - Such rows are permanent (append-only) and look genuine until someone reconciles them.
  - The same holds today for `decisya_entitlements`, so this change doubles the number of roles exposed.

**R-L-LOCK (the limit's book-row lock, G2 D2; T341-20).**
- What prevents it:
  - The lock is taken only after the body was read and validated, so a slow client cannot hold it.
  - No outbound call runs inside the transaction: book upsert, lock, count, insert, audit append, commit, all on one connection.
  - `RequestAborted` cancels the commands, and disposal rolls back.
  - Only the space's owner can create (`Ledger.Owner`).
  - The BFF's per-session `/api` rate limit bounds the number of waiters.
- What only detects it:
  - `decisya.ledger.requests{result="error"}` and spans tagged `decisya.ledger.result=error`.
  - No alert rule exists, and Postgres lock waits are not monitored.
- Where nothing contains it:
  - A create stalled inside its transaction (a slow database, process starvation, or a connection held mid-transaction) blocks that space's other creates for up to the 30 s command timeout. Each waiter gets the generic 500.
  - The waiters hold connections from the one `decisya_ledger` pool that every tenant shares, so a broad database slowdown can degrade every tenant's ledger requests, reads included.
  - There is no `lock_timeout` or `idle_in_transaction_session_timeout` (S341-02, backlog). The lock itself stays per space, so one tenant cannot block another tenant's creates by locking.

**ADR-0027 (money on the wire), own residuals.**
- What prevents it:
  - Input: the strict integer parse, the range check before any write, and the ordinal currency check before `TryFromCode`.
  - Output: `AccountMapper` refuses any amount outside ±(2^53 - 1) with the generic 500, never a rounded or clipped value.
  - `Money` refuses sub-minor digits at construction, so the conversions are exact.
- What only detects it: the contract test pins the documented range and shapes. A drift between the document and the code is caught there, but a behaviour drift would only be caught by the missing cases (G6-341-06, -07).
- Where nothing contains it:
  - The database has no range check on `opening_balance_minor`. A row written outside the API (owner SQL, a future migration) with an out-of-range value makes every read of that space's list fail with 500. That fails safe, but it denies service to that space.
  - From EP-04, a balance that sums past the range fails reads in the same way until EP-04 refuses such writes, as point 2 requires.
  - Amounts beyond 2^53 - 1 minor units cannot be expressed (accepted by the ADR).
