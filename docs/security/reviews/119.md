## Attacks on `release.yml`

- **Can a PR reach `packages: write` or `id-token: write`? No.**
  - Only `publish` holds those permissions (`release.yml:166-169`). The test asserts the per-job permission sets (`test_release.py:49-56`), and the top-level permissions are `{}` (`:33`).
  - `publish`, `verify` and `release-assets` are guarded to push or dispatch-on-main (`:163`, `:232`, `:275`).
  - Fork runs get a read-only token and no OIDC.
  - A same-repo branch that edits the workflow is the accepted T80-05 class: its SAN (`@refs/pull/…` or `@refs/heads/<branch>`) fails the exact identity.
- **Can a non-main ref reach them? No.**
  - `push` is limited to `main` (`:10-11`).
  - Dispatch is gated on `refs/heads/main` in `build` and `publish` (`:70`, `:163`).
  - A branch dispatch runs that branch's own file, which is again T80-05, and its SAN is rejected.
- **Can an expression reach `run:`? No.**
  - No `run:` line or block contains `${{`.
  - Action outputs reach the script only through `env:`, and each is regex-validated (`release_images.py:152-156`).
  - Step outputs are written only if they match `^[A-Za-z0-9._:-]*$` (`:867-875`).
  - Tool output is printed only inside `::stop-commands::` windows (`:132-139`).
- **Can the artifact handoff be swapped? No.**
  - Nothing is uploaded on PRs, so a fork cannot plant an artifact.
  - The download is exact and same-run.
  - The SHA-256 and the config digest are bound to `build`'s outputs before load, and the config digest is checked again after the push.
  - The residual is a malicious build step changing the archive or the step outputs after the scan, inside `build`. G3 already accepted this as T119-03 and backlogged it as S-119-06. This diff does not change that.
