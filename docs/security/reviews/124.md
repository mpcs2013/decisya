# Security review (combined light tier): Phase 0 hosting on the home NAS, ADR-0016 (issue #124)

- Scope: `docs/adr/0016-phase-0-hosting.md`, `docs/architecture/phase-0-hosting.md`, `docs/adr/README.md`, `docs/adr/0017-release-images-sdk-containers-cosign.md` (status line), and `docs/ai/pipeline/124.md` (read only). Reviewed with Read, Grep and Glob only. No Bash was used, so the change set comes from the orchestrator's list and the session's git status.
- Tier: Light (Marco, 2026-10-04). The change is docs-only. It is a decision record and changes no code, hook or permission. Every control it decides is implemented and tested in #120, #121, #122 and #30, and those issues run the full gates. So the light tier holds.
- Method: I reviewed the hosting choices as security decisions against the six questions in the review request and the release blockers in `docs/security/threat-models/system-baseline.md` (C-01, C-03, C-05, C-09, C-10, C-20). The product controls (BFF cookies, JWT, BOLA, validation, logging, AI lanes) and the dependency audit do not apply, because nothing in `src/` changes.
- Verdict: **PASS-WITH-NOTES.** There is no High. Before merge, fix the three Mediums and the four few-line Lows marked fix-now. All of them are edits to the two changed hosting documents. One re-check follows.

## 1. QuickConnect on (accepted risk)

> Re-check 2026-10-05: not applicable (QuickConnect disabled 2026-10-05, ADR-0016:59 and R9.13 :129). This replaces the accepted risk. DSM control still equals stack control, so the parts of G6-124-01 that bound DSM accounts and the shared folder still apply, and they are fixed.

The risk is acceptable for Phase 0 under three conditions: synthetic users only, nothing in the stack reachable from the internet, and the mitigations below recorded and applied. One point drives this: **DSM control equals stack control**. Through Container Manager, a DSM administrator reaches every secret file in `decisya-p0`, the Caddy root key, and the dumps, and the dumps include the key ring copy. The DSM firewall rule in R9.8 ("HTTPS 5001 from the LAN subnet only") does not bound QuickConnect. The relay reaches DSM over an outbound tunnel, so the firewall rule must not be read as a limit on DSM reachability. ADR-0016:170 already says so in its consequences.

ADR-0016:59 records only part of Marco's setup plan: "R9.9 (admin hardening, 2FA, auto-block) and no stack port exposed through it". R9.9 (:125) requires 2FA only on administrators. Finding G6-124-01 lists what is missing.

## 2. Caddy's internal CA

- The root key is **not backed up**. This is accepted and correct: it keeps the key out of off-site archives. Losing it costs one re-trust, which is documented at ADR-0016:103 and :172.
- **Trust in the BFF and Api through a read-only public-root mount** is accepted. These containers sit on `internal: true` networks with no egress, so the extra trust anchor cannot be used against any outbound connection they make.
- **"Certificate validation is never disabled"** is accepted. A #121 source test enforces it (note:146). That test must allow a `ServerCertificateCustomValidationCallback` that builds a chain with `X509ChainTrustMode.CustomRootTrust` against the mounted root, and reject only callbacks that accept everything.
- **Is the blast radius of a stolen root key bounded? Not yet.** The root can sign for any name. The documents allow Firefox's enterprise-roots setting (ADR-0016:71, note:98, manifest:19). That setting only works if the root is in the operating system store. Every application on the device then trusts the root, which defeats the "prefer Firefox's own store" consequence at ADR-0016:171. The key can be stolen through DSM, and DSM is reachable through QuickConnect. A stolen key would let an attacker intercept Marco's banking and e-mail from any network position he shares with the attacker. Finding G6-124-02 limits the scope and the lifetime of the trust now. A name-constrained CA is a SHOULD for #120 (B-1).

## 3. The back channel through Caddy's network alias

The design is sound in principle. The issuer is the same on the front channel and the back channel, the certificate is validated, and `KC_HOSTNAME_BACKCHANNEL_DYNAMIC` is not needed. **The widening has no scope, though.** The documents widen `remote_ip` to "the internal network" for every site block (ADR-0016:124, note:81, note:128). They put the aliases for both `id.p0` and `app.p0` on "the internal network" (note:97). They restrict the admin console only "by `remote_ip`" without naming a range (note:129).

As written, Postgres, Redis, the OTel collector, the migrator and the backup job could all reach the Keycloak admin console and the `master` realm through Caddy, and so could every device on the home LAN. C-03 lists "a published admin console" as a release blocker. Finding G6-124-03 sets the scope.

## 4. The R9 isolation list

- **Docker publishing bypasses the DSM firewall, and Caddy's `remote_ip` is the actual control.** This is recorded correctly at ADR-0016:124 and :176, and #120 verifies it from outside the range. The control works only if Docker keeps the LAN source addresses. #122 already asks #120 to confirm this (note:130). G6-124-03 says what happens if the addresses are not kept. G6-124-06 binds the published port to one interface.
- **SSH for `mpcs_nas` (key only, LAN only, off when not in use)** is recorded at ADR-0016:125. DSM 7 has no setting for key-only SSH, so it needs an `sshd_config` edit, and ADR-0016:85 itself notes that DSM updates revert such edits. G6-124-06 adds a re-check.
- **The other project on the NAS** (manifest:13) is not mentioned in ADR-0016. R9.1 bounds what the stack user can reach. Nothing yet bounds what the other project's accounts can reach in `decisya-p0`, and the R9.8 firewall ("deny the rest") does not mention the service that receives the other project's backups. Both are covered in G6-124-01.
- The rest of R9 is accepted as written: no socket mount, no host paths outside the dedicated folder, no privileges, capabilities, devices or host namespaces, no port-forward or UPnP, and resource limits. The guard tests in note:140-145 enforce it.

## 5. Fallback triggers F1 to F6

These are accepted as triggers. F5 (end of security updates) and F6 (an R9 MUST that cannot be met on DSM) are the security-relevant ones, and both are present. F4 measures swap growth as an absolute 2100 MB, derived from the 1844 MB measured on 2026-10-04. Swap use drops after a reboot. Measured from a fresh baseline, the absolute threshold could hide about 2 GB of growth, and F4 would never fire. This is finding G6-124-07. A trigger for a Critical DSM or QuickConnect advisory is a SHOULD (B-5).

## 6. Consistency

- ADR-0016's status (Accepted, 2026-10-05), the README row (`docs/adr/README.md:22`) and the architecture note (:5) agree. ADR-0017's status line and README row agree (Accepted, #119 G2).
- ADR-0007: R7 meets the S3-compatible, no-lock-in rule and the restore drill (#30). ADR-0011 is not affected, because the deployment target is not the development environment. ADR-0014: digest pins are kept.
- **ADR-0015 conflict.** ADR-0016:78 and note:99 say the stock Caddy image is "scanned with the other third-party images". ADR-0015 §2 scans only the `postgres`, `keycloak` and `redis` aliases from `ContainerImages.cs`, and anything else fails closed. Caddy and the OTel collector are therefore not scanned, and nothing ties the digests in the deploy Compose file to the scanned references. This is finding G6-124-04.
- **Internal inconsistency on the key ring.** note:130 says the key ring is "mounted into the BFF only", yet the backup job copies it, and note:70 (`BJ --- KR`) shows the backup job attached to it. This is finding G6-124-05.
- Editorial, not a security finding: `docs/adr/0017-release-images-sdk-containers-cosign.md:10` still calls ADR-0016 "Proposed". Update it while the status line is being edited, or leave it as dated context. Re-check 2026-10-05: fixed, ADR-0017:10 now reads "Accepted 2026-10-05".

## Backlog (SHOULD, to #83 or to the named issue's G3; none changes the merge decision)

- **B-1 (#120 G3): name-constrained CA.** Generate a root offline with `nameConstraints` permitting `p0.home.arpa`, and keep its key off the NAS. Give Caddy a constrained intermediate through its `pki` CA `intermediate` certificate and key settings. Constraining the intermediate is enforced by every verifier in scope. The cost is rotating the intermediate by hand. If this works, a stolen key on the NAS is limited to `*.p0.home.arpa`.
- **B-2 (#120): run the Caddy container as non-root.** Caddy holds the CA key and port 8443 needs no privileged port. Also set `skip_install_trust`.
- **B-3 (#121 G3): limit the trusted proxy.** Set Keycloak's `proxy-trusted-addresses` to Caddy's back-channel address, so `X-Forwarded-*` from any other container is ignored (this matters for C-10 event IPs). In .NET, trust the mounted root per back-channel `HttpClient` with `CustomRootTrust`, rather than process-wide through `SSL_CERT_FILE`.
- **B-4: not applicable (QuickConnect disabled 2026-10-05).** Original text: **daily DSM account.** Give Marco a non-administrator account for everyday QuickConnect use and turn on DSM sign-in notifications. Then a phished QuickConnect session is not a DSM administrator session.
- **B-5: not applicable (QuickConnect disabled 2026-10-05).** Original text: **advisory trigger.** Add a review trigger: a Critical Synology advisory for DSM or QuickConnect that is not patched within 7 days means QuickConnect goes off, the first lever named in ADR-0016:59.
- **B-6 (#120 G3, Low, found at re-check): direct Keycloak reachability on the back-channel network.** G6-124-03(a), as I wrote it and as R9.6 (ADR-0016:122) and note:146 apply it, puts Keycloak on the back-channel network with the BFF and the Api. Those two can then reach Keycloak's HTTP listener, including `/admin/*` and `/realms/master/*`, and its management port 9000 directly, without passing Caddy's `remote_ip` rules. Exploiting this needs code execution in the BFF or the Api, and master-realm admin credentials as well. Fix in #120: keep the back-channel network to Caddy, the BFF and the Api only, and put Caddy and Keycloak on their own `internal: true` network. Then update R9.6 and the note:146 guard to match.
