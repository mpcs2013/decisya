## Rulings asked for

1. **`ScanExclusions` `.pyc`/`.pyo` skip and G4-77-03.** Yes, a recorded note is needed. G4-77-03 says "only the `.git/` skip", and both the #26 `node_modules` skip and this one widen it. G4-77-09 says a widening needs G3. I ratify both as narrow and pinned (exact directory for `node_modules`; exact extension and immediate `__pycache__` parent for bytecode; `ScanExclusionsTests` rows). The note is in `realm-guard-scope.md`, section "G6 ruling for #121". The ratification holds once F-03 is fixed. **Satisfied at the re-check (2026-10-08):** F-03 is fixed, and the bytecode skip is ratified.
2. **Address scan skips `deploy/keycloak/production/common-passwords.txt`.** Accepted. The match is an exact, case-sensitive relative path, not a suffix or folder, and the skip set is pinned to that one entry (`test_no_home_addresses.py` `SkipPathTests`). The file's SHA-256, size and line count are pinned to Marco's approval in the same always-run `deploy-guards` job, so any change to the skipped file fails CI. The flagged entries are upstream data, not a home address.
3. **`realm rebuild` running `DROP DATABASE … WITH (FORCE)`.** Accepted for Phase 0. The database name is a constant. The identity check gates it and fails closed on every failure path. It refuses with a retired bootstrap secret, so it never leaves Keycloak without an admin. It prints no value and stops at the first failed step. It stays a Phase 0 stop-gap that the go-live gate C-03b retires. The check runs before `stop keycloak`, so there is a window of seconds in which an admin could create a user. That is negligible while the console is workstation-only, and it is not a finding.
4. **`assemble` copies `identity-check.sql` into the stack.** Accepted. The file is not mounted into any container. It is covered by the manifest hash that `check` verifies, and it is sent to psql over stdin only after the static check. Anyone who can edit the stack copy already holds the superuser secret in the same 0700 folder, so the copy adds no privilege.
5. **`ClaimActions.Remove("acr")` in the BFF.** Accepted. The claim comes from the validated ID token (`MapInboundClaims = false`, no UserInfo). It lives only in the server-side ticket in Redis; the cookie still carries only the session key, which `SessionFixationGuard` depends on and which is unaffected. `/bff/me` returns fixed fields (`sub`, `email`, `tenant_id`), so the SPA never sees it. No BFF decision reads it. The Api, using the access token, stays the only enforcement point.
6. **Devops findings.**
   - **One `passwordBlacklist` per policy:** accepted as a go-live item, not a #121 merge item. Go-live gate B3 already says the breached list must be a superset file and that `identity-check.sql` row 12, the realm and the tests change in the same PR.
   - **No "BFF client exists" key:** B-01 (backlog). The gap fails closed.
   - **`kcadm.sh` unusable for OTP admins:** accepted. It is the intended effect of C-01, and the go-live gate (line 74) already sends operators to the console. It must not be worked around with a password-only master admin or a master service-account client without a G3 ruling. F-01 makes `verify` catch the second.
