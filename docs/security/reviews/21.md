## Checks the orchestrator asked for

- **JIT race fix (`TenantMembershipGate.cs:67-81`).** Correct. The winner inserts `tenants` and `memberships` in one `SaveChanges`, so under READ COMMITTED the two rows become visible together. Each later statement takes a fresh snapshot. Once the loser's tenant read sees the winner's commit, the next membership read sees the winner's membership too. A same-user loser therefore gets `Member`, and a different-user loser gets `Refused` with no row written. If the tenant read is still earlier than the commit, the insert waits and gets `23505` only after the commit, and the one re-read sees the membership. The old order (membership first) could straddle the commit, as the comment says. EF orders the tenant insert before the membership insert (FK), so the first conflict raised is `PK_tenants`.
- **SCRAM verifier and role provisioning (`ScramSha256Verifier.cs`, `MigrationRunner.cs:65-110`).**
  - The verifier follows RFC 5802/7677 exactly: 16-byte CSPRNG salt, PBKDF2-HMAC-SHA-256 with 4096 iterations, `StoredKey = H(HMAC(SP,"Client Key"))`, `ServerKey = HMAC(SP,"Server Key")`, and Postgres's text form. The round trip is proved against a live server.
  - The plaintext never enters SQL. The verifier is a bound parameter to `SELECT format('… %I … %L', @role, @verifier)`, so no client-side interpolation happens. Identifiers are module constants or the connection's own database name, quoted with `QuoteIdentifier`.
  - The role statement is `LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE NOINHERIT NOREPLICATION NOBYPASSRLS`. `REVOKE ALL ON DATABASE … FROM PUBLIC` also removes PUBLIC's TEMP, then `CONNECT` is granted to the role. The schema gets `USAGE` only, the tables get DML only, and the history table is revoked. All of this is reapplied on every start. `duplicate_object` is caught only for `CREATE ROLE`.
  - The only log messages are the key-only configuration error and a fixed completion line. Exceptions outside `InvalidOperationException` go unhandled to stderr, which carries Npgsql or EF messages (host and port at most, never a password). The EF logger factory is not attached (`MigratorLogTests`).
- **AppHost connection-string split (`AppHost.cs`).** `WithReference(decisyaDb)` and `Migrator__TenancyRolePassword` go only on `decisya-migrator`. `decisya-api` gets exactly one `ConnectionStrings__tenancy`, built with `ReferenceExpression`, `Username=decisya_tenancy` and the secret, persisted, alphanumeric parameter. It waits for the migrator to complete, and it has no `WithReference` to `postgres` or `decisya`. This is pinned statically (`AppHostConfigurationTests`) and on a running AppHost (`TenancyMigratorResourceTests`). The alphanumeric parameter cannot inject connection-string keywords.
- **403 shapes.** The middleware 403s (`CallerContextMiddleware`, `TenantMembershipMiddleware`) set only `Status`, and the default writer adds `type`, `title` and `traceId`. Both set `no-store`. The reason goes only to the log, as a fixed event (2000, 2001, 2101, 2102). The policy 403 has an empty body.
- **No secret, connection string or raw `sub` logged.**
  - Every new `LoggerMessage` (`CallerContextMiddlewareLog`, `TenantMembershipGateLog`, `ConcurrencyConflictExceptionHandlerLog`, `MigratorLog`) is parameterless or carries only the key-naming reason.
  - Enrichment gets `identity.UserId` and hashes it inside `LogEnrichmentContext.Begin`.
  - `AddTenancyModule` fails with the key name only.
  - The tracing sources stay `Decisya.*`: there is no Npgsql command-text span.
  - The raw `sub` appears only in the Owner-only `MemberDto`, as G2 specifies.
