## Line-by-line record (G3 M-5, required by the issue)

I read each function below in full in `.github/scripts/image_scan.py` at `HEAD`, and its diff against `main`.

**Mode selection**
- `changed_files` (`:790-796`):
  - argv list `diff --name-only --no-renames -z HEAD^1 HEAD` through `_git` (`:782-787`: no shell, `cwd=ROOT`, timeout);
  - any failure gives `None`.
  - A non-UTF-8 name decodes with replacement characters, so it can never equal a classified path. Under `.github/image-scan/` it is unclassified and runs the full scan. Under `.github/release/` it scans nothing, which is Q8 as accepted.
- `is_merge_commit` (`:799-804`): true only when `HEAD^2^{commit}` resolves and `HEAD^3^{commit}` does not. If git cannot run, it is false. `fetch-depth: 2` in `ci.yml` provides both parents.
- `select_mode` (`:815-835`), first match wins:
  - not `pull_request`, not a merge commit, unknown base, or an empty lane: full;
  - any lane path outside {pin, parity, exceptions, `GATE_FILES`, `.github/release/`}: full;
  - any gate file: gate-change, which beats delta and validator;
  - exactly `{exceptions.json}`: validator;
  - otherwise delta.

  This matches the M-2 table plus M222-2.
- `run()` mode handling (`:1119-1137`, `:1159-1176`):
  - It reads only `GITHUB_EVENT_NAME`, `RUNNER_TEMP` and `GITHUB_STEP_SUMMARY`, and none of these widens a decision.
  - In delta mode, if the base pins cannot be read at `HEAD^1`, the run falls back to full.
  - Validator mode, and delta mode with no changed alias, return before the database update.
  - Exactly one `db update` runs (`:1145`), before any scan, for both sides (Ruling C).

**Base loading**
- `load_base_module` (`:854-892`):
  - It refuses a link on each path component and a missing file.
  - It requires `git -C .image-scan-base rev-parse --verify HEAD` to equal `HEAD^1`. With no checkout, `-C` resolves to the head repository, returns the merge commit and fails.
  - It loads the module under `_decisya_base_image_scan` with `exec_module` and never registers it in `sys.modules`.
  - Any `BaseException` during the load or the `BASE_API` `hasattr` probe gives `None`. Only `KeyboardInterrupt` re-raises.
- `base_inputs` (`:895-907`): the base reads its own pins and scanner reference. The results are type-checked and copied, and any `BaseException` gives `None`.
- `run()` (`:1160-1170`):
  - If the base cannot read its inputs, there is no base.
  - In delta mode, base pins that differ from `git show HEAD^1:` mean no base.
  - In gate-change mode, no base fails the check (deviation 1 below).
- `head_api` (`:910-914`): the head's own functions under the `BASE_API` names, so the head scan uses the same code path as the base scan.
- `scan_with` (`:917-942`):
  - Every call into `mod` (`scan_argv`, `_run`, `check_provenance`, the lazy `read_sbom`) and every use of its return values sits inside one `try`, so any `BaseException` becomes a reason.
  - The scanner JSON is parsed by the head.
  - The per-alias folder is always removed.

**Comparison**
- `finding_key` / `item_key` (`:949-960`): exact (alias, `artifact.name`, `artifact.type`, `vulnerability.id`). Non-strings map to `""` on both sides alike, and `evaluate` now emits `"type"` (`:669`).
- `base_ranks` (`:972-984`):
  - The base's `evaluate` sees one raw match at a time, with no exceptions. It decides only the severity class, including S-05 elevation (Ruling A).
  - The key comes from the raw match, computed by the head, so the base cannot shape a key.
  - A label `rank_of` does not know is not counted, so the head finding stays new (fail closed).
- `new_findings` (`:987-997`):
  - `None` ranks: everything is new.
  - Otherwise, a finding is new if its key is absent, its rank is unknown, or its rank is higher than at the base.
  - Related ids never match (M-2).
- `compare_alias` (`:1011-1076`):
  - A failed head scan goes into `failed`.
  - A re-pointed alias or a new alias (`same_repository`, `:1005-1008`) makes every head finding new.
  - A failed base scan, another database build (`:1044-1045`, Ruling C) or a base classification that raises (`:1047-1052`, M222-1) makes the base unavailable.
  - S-1 (`:1054-1057`): in gate-change mode with an unchanged scanner and reference, an unavailable base fails the check.
  - R-1 (`:1065-1075`): with an unchanged scanner and reference, a raw base key (any severity) missing at the head fails. Otherwise it is only logged.
- `main` (`:1179-1187`): it re-raises `SystemExit`, but no base call can reach it, because every base call is contained above (M222-1).
