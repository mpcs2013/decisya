## D-1 (`.github/image-scan/exceptions.json`)

Not a merge blocker: the entries existed before this PR, the PR only rewrites the justifications for the deployed context, and nothing deploys at merge. The libc6 entries for `api` and `bff` follow the widened rule (Marco's approval 2026-10-05, 30-day expiry 2026-11-04); the G7 PR body must carry that approval line, as S-120-07 requires.

The six `NEEDS CONFIRMATION` entries (zlib on `postgres` and `redis`, `pcre2` and `pcre2-syntax` on `keycloak`) must be confirmed **before the first `stackctl.py up` that binds Caddy to a LAN-reachable address**. In practice that is the #132 NAS bring-up, or the #120 local Linux proof if it binds to a LAN interface rather than loopback. In any case it must happen before the entries expire on 2026-11-02, and they are not renewed without it. What to confirm, recorded in the #132 manifest and in the justification text (with the `NEEDS CONFIRMATION` words removed):

1. **Keycloak `pcre2` / `pcre2-syntax` (CVE-2026-86145, -89161, -103111):** the Grype match location is the OS package database (not a JAR), and the running Keycloak JVM does not map `libpcre2` (no `libpcre2` line in `/proc/<java pid>/maps` inside the container). Keycloak is on the LAN request path, so if either check fails, the entry falls under the 30-day rule with Marco's recorded approval, or the deploy waits for a fixed digest.
2. **Redis `zlib` (CVE-2026-85091):** the match location is the OS package, and `redis-server` neither links nor maps `libz` (`/proc/1/maps`). If it does, only the exposure argument remains, and the entry is not renewed.
3. **Postgres `zlib` (CVE-2026-85091):** the server links zlib, so the CVE's affected function and vector must show that exploitation needs attacker-controlled compressed input that none of the three authenticated clients (migrator, Api, Keycloak) can send. None of them holds `REPLICATION`, which keeps out server-side compressed base backups. If the vector is reachable by an authenticated role, wait for a fixed digest.
