## Residual risk of the waived cooldown (full scope, restated after G4)

- **The threat.** A hijacked, malicious or broken `26.8.2` index (pushed 2026-11-19 07:42 UTC) is run before the community has had the seven days to notice. The cooldown ends 2026-11-26 07:42 UTC.
- **What has already run inside the cooldown, on Marco's host.**
  - The M-2 throwaway container, `--network none` with a throwaway admin. This was contained apart from the shared Docker engine.
  - The Identity suite's Testcontainers: 402 tests, network-enabled, the fixtures' test values, the shared Docker engine. AetherSpark's stack was down at the time.
  - The AppHost suite. I did not check which of its tests started the Keycloak container.

  The persistent `decisya-keycloak` container, which holds the dev secrets and the `keycloak` role on the dev Postgres volume, has not been recreated yet. Under S-1 and the M-3 (d) owner step it is recreated only after the cooldown ends.
- **What prevents:**
  - The digest pin: what was scanned, tested and reviewed is byte-for-byte what runs.
  - M-1's two-way read (done; both equal).
  - The official `quay.io/keycloak` repository.
  - No deploy is possible: guava (D-008) and the strict full scan keep the gate shut.
  - D-C: `main` never carries the pin before the cooldown ends.
- **What only detects:**
  - Grype: known CVEs only, never a planted payload.
  - The suites: broken behaviour, not a stealthy payload.
  - Ostium's independent use of the same digest (O-047): a second consumer, not a Decisya control.
  - The S-1 re-read of the tag and the advisory check at merge. After the merge, nothing in Decisya watches for a retraction or a rebuild except a person looking.
- **What nothing in Decisya contains.**
  - If the image were malicious, the Testcontainers runs already done could have read the fixtures' test values. They could have reached what a container on the default Docker network reaches, including outbound internet.
  - The only boundaries were Docker Desktop's VM and the host firewall; Decisya has no egress control for dev or test containers.
  - The same holds for the persistent dev container once it is recreated. By then the cooldown has passed, which lowers the likelihood but contains nothing more.
  - CI runs on GitHub's ephemeral runners with synthetic data, and the job token is not passed into the container.
  - **Impact if it happened:** dev and test values and synthetic data leak, and the dev secrets would then have to be rotated. Production secrets do not exist yet.
