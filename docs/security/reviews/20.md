# Security review – issue #20: 0.08 API host JWT bearer validation

- Mode: diff review (G6), ASVS 5.0 L2, L3 for V6 and V7.
- Scope: `git diff origin/main...HEAD` at 246025e (50 files: `src/Decisya.Api/**`, `src/Decisya.AppHost/AppHost.cs`, `src/Decisya.ServiceDefaults/Extensions.cs`, `.github/workflows/ci.yml`, `tests/Decisya.Api.Tests/**`, the AppHost and ServiceDefaults tests, the #20 docs). The working tree is clean.
- Checked against: G3 MUSTs G4-20-01 to 05, the fix-now SHOULDs S-1 to S-3 and the G6 checks in `docs/security/threat-models/api-jwt-validation.md`, and the CLAUDE.md security principles. B-1 to B-5 are already on #83, so they are not repeated here.
- Not re-audited: #18 and #19 (BFF session, forwarding, refresh).
- Reviewer: security-reviewer agent, 2026-09-28. No secret value was read. The one runtime probe (below) used a random throwaway `UserIdHashKey` passed through an environment variable.

## Verdict

**PASS-WITH-NOTES.** The API is safe to merge. It meets every G3 design point, and there are no High or Medium findings.
- Only an RS256 or ES256 access token for `decisya-api`, from the pinned issuer and with `typ: Bearer`, authenticates. Clock skew is 60 s.
- Every rejection is the same bare `401` with `WWW-Authenticate: Bearer`.
- The fallback policy denies by default. Identity comes from claims only.
- `UseExceptionHandler` runs first in every environment.
- The AppHost gives the API no secret.

Two Low findings are **fix-now**. Both are test-only changes of a few lines, in files this PR creates:
- **F1:** the Keycloak-outage test pins a 500 that production does not produce.
- **F2:** after the flake fix, no test proves that a bad configuration still stops startup.

F3 is a Low for backlog #83.

## Rated items (orchestrator)

1. **The metadata-outage deviation. Severity Low, fix-now: F1.**
   - Leave the product code alone. Production already returns the bare 401 that G4-20-02 required (see F1's probe), and needs neither a try/catch nor a 503.
   - The 500 would have been acceptable in itself, because nothing leaked. But it was a test-harness artefact, and the test currently guards a code path that production doesn't use. Fixing the test is a few lines in a file this PR creates.
   - A 503 for the outage is not recommended. It would differ from the other rejections and so tell an attacker that the API cannot reach Keycloak. Surfacing the outage to operators is a telemetry question for 0.17 at the earliest, not a status code.
2. **The two flake fixes.**
   - **`ApiJwtOptionsTests` (validators called directly): yes, this weakens what G3 asked.** The validation rules are still proved, but "startup fails" is not. F2 restores it without starting a host.
   - **NFR-27 at 45 s and 75 s plus the pinned 60 s: no weakening. Accepted.** `JwtBearerOptionsPinnedTests` pins `ClockSkew == 60 s` exactly, with no clock involved. The 45 s and 75 s rows prove that the handler really applies that skew: 75 s would pass under the 300 s default. Together they prove what the 59 s and 61 s pair proved, without its timing race. G2's "don't widen the margin" was meant to stop the tests from hiding a wrong skew, and the pinned test keeps that.
3. **The renamed constant in `CallerIdentityTests`: accepted, no finding.**
   - The value `7c9e6679-…0ae7` is `dev-alice`'s public seeded tenant id. It is in `deploy/keycloak/decisya-realm.json:179` and `docs/architecture/keycloak-realm.md:177`, so it is not a secret.
   - Renaming it rather than adding an allowlist entry is the right choice: `.gitleaks.toml` is unchanged by this PR, so detection stays at full strength.
   - `gitleaks detect --log-opts=origin/main..HEAD` found no leaks in either commit.

## Checks that passed (evidence only, no action)

- **G4-20-01 (T-01 to T-04).**
  - `JwtBearerOptionsSetup.cs:44-62` sets the whole G3 parameter set, including `ValidAlgorithms = {RS256, ES256}` and `ClockSkew` 60 s. `OnTokenValidated` fails any token whose `typ` claim is not an ordinal match for `Bearer`, at the authentication stage.
  - `InvalidTokenCaseCatalog` covers every G3 row. `none`, `None` and `NONE` each appear with and without a signature. HS256 is keyed with the PEM and with the DER form of the public key. PS256 and RS512 use the genuine key. The catalog also has an embedded `jwk`, an unknown `kid` or second key, no `exp`, `nbf` in the future, `typ: ID`, no `typ` and a wrong issuer.
  - `JwtBearerOptionsPinnedTests` pins the parameters. Harness B confirms that real access tokens carry `typ: Bearer`.
- **G4-20-02.**
  - The environment validator fails outside Development on a non-https authority or a relaxed flag, and its messages name the key only.
  - `IsLoopbackAuthority` matches `Uri.Host` exactly. Its `"::1"` branch never matches (G3 answer 1), which fails closed.
  - The loopback theory covers `localhost.evil.test`, `localhost@evil.test`, `127.0.0.1.nip.io` and `keycloak`.
  - The startup wiring is not yet proved: F2.
- **G4-20-03.** `IncludeErrorDetails = false`, and no event writes a body. `ChallengeResponseTests` compares every negative row, plus `Basic`, an empty `Bearer` and `Bearer not.a.jwt`, against the no-token response. `CallerIdentity.From` returns null on a missing, blank or duplicate `sub` or `tenant_id` (S-2), which gives a generic 403 ProblemDetails.
- **G4-20-04.**
  - The fallback policy requires an authenticated user with a `sub` claim.
  - Only `/health` and `/alive` call `.AllowAnonymous()`, and ServiceDefaults maps them only in Development.
  - `CallerIdentity` never reads `Request.Headers`.
  - Nothing in `src/` calls `UseForwardedHeaders` or sets `FORWARDEDHEADERS_ENABLED`.
- **G4-20-05.**
  - `UseExceptionHandler()` is the first middleware (`Program.cs:20`), after `AddProblemDetails`.
  - `ExceptionHandlingTests` covers {Development, Production} × {html, json}. It asserts that the canary, the token and the string `Authorization` are all absent from the body.
  - It has no "no `Accept`" row and does not check headers. Both are minor and don't change the merge decision.
- **G6 static checks.**
  - `src/**` contains no assignment to `ShowPII`, `LogCompleteSecurityArtifact`, `RefreshInterval` or `AutomaticRefreshInterval`.
  - `Decisya.Api` makes no logger call at all.
  - `SaveToken = false`.
  - The AppHost gives the API only `Api__Jwt__Authority` and `WaitFor(keycloak)`, with no `WithReference`. `AppHostResourceTests` asserts that it carries no secret variables and no `services__keycloak__*` (S-3).
- **Dependencies.** `dotnet list src/Decisya.Api package --vulnerable --include-transitive` reports no vulnerable packages. The only new reference is the first-party `Microsoft.AspNetCore.Authentication.JwtBearer` 10.0.12, which was already pinned. This PR has no npm changes.
- **CI.** `ci.yml` only adds `Decisya.Api.Tests` to the existing Integration loop. The existing masked, generated secrets are unchanged.
