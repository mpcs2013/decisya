## The G5 caution: does the missing smoke run change the merge decision?

No. It is a pre-#132 run, not a pre-merge one.

- Merging deploys nothing. The stack first runs on the NAS in #132, and step 9 of the runbook (the smoke) is already the run that clears the **(unverified)** marks.
- Admission on 8443 does not depend on Caddy normalising the way the model assumes. Every admitting route is a positive allow-list, followed by a catch-all 403. If Caddy's matching differed from the model, the result would be a refusal, not an admission. The one way through would be a parser differential, where Caddy reads a path as `/realms/decisya/…` or `/resources/…` and Keycloak resolves it to `/admin…` or `/realms/master…`. That needs a dot segment or a double encoding, and three rules cover those before any admitting route:
  - route 2 matches the cleaned view;
  - `@dotdot` refuses any `..` left after cleaning;
  - `@encoded` refuses a `%2e`, `%2f` or `%5c` left after the single decode.
- D3 fails closed if it is wrong: a console that builds 8443 URLs breaks, because 8443 refuses the admin paths.

**Condition for #132** (for the orchestrator to carry into the #132 manifest): `deploy/tests/stack_smoke.py` runs green on a Linux Docker host before the first `up` on the NAS. The record must include the 8443 variant rows, the 8444 rows, the "console page names the 8444 origin" row and the two container rows. A failed variant row is a High against the edge, to be reported at once. It does not go to backlog.

## The test fixture: bootstrap password on `kcadm.sh` argv

Acceptable for a test fixture. No change is needed.

- The value is a fresh random value for each run (`Hex(24)` from `RandomNumberGenerator`, `ProductionKeycloakStack.cs:129`). It exists only in a Testcontainers Keycloak that is destroyed after the run. The fixture already sends the same value in-process for its token request (`:280`).
- The `$(cat …)` expands inside the container's `sh -c`. The argv therefore never exists in the test process, its logs or the xUnit output. Inside the container it is visible only for the seconds `kcadm.sh config credentials` runs. The only other party that could see it is root on the Docker host or VM, which can read the mounted secret file anyway.
- The failure message carries `kcadm.sh`'s stderr (truncated to 600 characters). `kcadm.sh` does not echo the password, and the shell runs without `-x`.
- The operator path is unchanged and correct. The runbook's CLI column prompts for the password (`exec -it … config credentials` with no `--password`) and never puts it on a command line.
