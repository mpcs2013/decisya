## Rulings on the orchestrator's eight points

1. **Placeholder change `${env.X}` → `${X}`: the T-01 guard is still complete for every launch path that exists.**
   - AppHost start check: `RealmSecretRules.EnsureDevUserPassword` (`AppHost.cs:4`) runs before any resource and throws on missing, blank or rule-violating values. Its message names the key and the rule, never the value, and `RealmSecretRulesTests.cs:119-120` proves a canary is absent from `Message` and `ToString()`. The other two parameters are generated (`MinLength = 32`, `Special = false`, persisted), so they are always present.
   - Fixture: it always sets both values, fails in CI when either is unset, and fails everywhere when a value is set but invalid. `KeycloakRealmFixtureSecretResolutionTests` covers the three branches, but see G6-01 for where the resolution runs.
   - Secret equality: `RealmConfigurationTests.cs:200-219` compares the stored client secret with `CryptographicOperations.FixedTimeEquals` and asserts on the boolean only.
   - Positive login: the `BffLoginFlowTests` code flows log in dev-alice, dev-bob and dev-admin with the environment value. That proves the password placeholder is substituted.
   - Regression: `PlaceholderSubstitutionRegressionTests` requires HTTP 200 **and** "Invalid username or password." for the `${X}` literal, the `${env.X}` literal and an empty password. Each case runs in its own container with fresh values. Pinning Keycloak's own message is the right design: an unrelated failure, such as the cookie bug, can't pass for a rejection.
   - Static test: `RealmExportFileTests` requires the distinct `${…}` tokens to be exactly the two `${X}` constants. A `:default` suffix, a third variable or a reverted `${env.…}` form fails. The realm file uses literal display names, so none of Keycloak's `${…}` message keys can collide.
   - Residual: G6-03 (unset behaviour of the new form not recorded). A client secret the user sets manually is not charset-checked by the AppHost; that is G2 design and Low, because the generated default always passes.
2. **`SecureCookieRelayHandler` is test-only and silent: confirmed.**
   - It is `internal` in `Decisya.Identity.Tests`, and it is referenced only by `BffLoginFlowTests`, `PlaceholderSubstitutionRegressionTests` and `TenantSelfEditTests`.
   - No `src/` project references the test project. `ApiBoundaryTests` now forbids `Testcontainers` namespaces in `Decisya.Api`, `Decisya.ServiceDefaults` and `Decisya.SharedKernel`.
   - It has no logging, output-helper or exception path that carries a cookie value. It stores only the `name=value` pair, in memory, per `HttpClient`.
   - It disables auto-redirect, and every client using it has a loopback Testcontainers `BaseAddress`. The jar isn't host-scoped, but no test sends its client off that origin: the JWKS fetch uses `PathAndQuery`.
   - Keep it that way. If a future test needs a second origin, scope the jar by host first.
3. **The https issuer under Aspire auto-HTTPS: adequate for dev, with G6-02 and G6-05.**
   - In the AppHost, https on host port 8080 (container port 8443) is stronger than G3 assumed.
   - Testcontainers stays on http on loopback, which `sslRequired: external` allows.
   - `sslRequired: all` would break the Testcontainers flows, so `external` remains right for #17. It is adequate only while every published port is loopback-bound, and that is what G6-02 must re-prove after the persistent change.
   - The management port 9000 is TLS as well (the #70 symptom) and was shown as `127.0.0.1` in the earlier evidence.
   - The tests assert only the `/realms/decisya` suffix of the issuer. That is correct, because the scheme differs between the two launch paths.
   - #20 must take the exact issuer from configuration or the Keycloak endpoint reference (G2 lines 518-523; F-3). It must never use a suffix match or a hard-coded scheme. Carry that to #20 as a MUST.
4. **The `.gitleaks.toml` digest allowlist is narrow: confirmed.**
   - `condition = "AND"`: the path must be exactly `^src/Decisya\.AppHost/ContainerImages\.cs$`, and, with `regexTarget = "line"`, the whole line must be `^\s*public const string \w+Sha256 = "[0-9a-f]{64}";\s*$`.
   - G4 proved that the same digest in any other file is still flagged.
   - Splitting the old `[allowlist]` into two `[[allowlists]]` tables keeps its OR semantics unchanged.
   - No path allowlist covers `deploy/`. The `${env.DECISYA_…}` regex allowance that G3 pre-authorised was not needed and was not added (G4-17-04).
5. **Persistent containers and AppHost-test isolation: sound. An outside override can't cross a privilege boundary, but it can undo the incident fix.** See G6-04.
   - The tests pass a GUID-named throwaway volume plus `UseEphemeralContainers=true`, bound their waits at 3 minutes and clean up in `finally`.
   - `RemoveVolumeAsync` refuses the protected name. It calls `docker` through `ArgumentList` with no shell, and discards the output.
   - An outside override (environment, user-secrets, launch profile) needs Marco's own account, which already controls Docker. The one harmful combination, ephemeral mode on the default volume, deserves a start-time refusal.
   - A crafted volume name reaches Docker as a DCP volume name, not a shell string, so there is no injection path.
6. **ci.yml Integration step: meets G4-17-19.**
   - Only the Integration step changes.
   - Both values come from `openssl rand -hex 24` (48 hex characters, inside both `RealmSecretRules` ranges). Each is `::add-mask::`ed before any other use.
   - They are plain shell variables, passed as a command prefix to the one `dotnet test` call only. There is no `export`, `$GITHUB_ENV`, `$GITHUB_OUTPUT`, `set -x` or `secrets.` reference.
   - `--ignore-exit-code 8` and its TODO are gone. No `upload-artifact` step exists, so the TRX files stay on the runner.
   - No `permissions:`, trigger or action changes.
   - Open: G6-01 (the unit step) and G6-08 (the CI count evidence).
7. **The #70 skip on `KeycloakResourceTests`: acceptable.**
   - The Done-when (import on start, login page reachable) was verified live on a fresh import, with a 200 from `curl`, a dev-alice login to a code, and a rejected literal placeholder. The Testcontainers suite proves the same realm behaviour automatically in CI.
   - The static `AppHost_cs_passes_secrets_only_through_parameters` test and `ContainerImageParityTests` cover what the skipped test would add for secret wiring and image identity.
   - The skip reason names #70 and the removal condition. #70 must remove the skip, not widen it. Don't "fix" it by disabling TLS verification on the health check.
8. **The G5-kept test files and the new parity case: accepted, with G6-07 hardening.**
   - `KeycloakDbInitScriptTests` covers every G4-17-15 bullet: `set -eu` first, the unset guard before psql, no trace or echo outside comments, the quoted heredoc, `\getenv`, the raw variable exactly once in the heredoc, both `SET` lines, the role attributes, `REVOKE … FROM PUBLIC`, LF only.
   - `KeycloakRealmFixtureSecretResolutionTests` covers G3 change 1's three branches and restores the environment. It runs in the unit step, where it is safe, because the shared fixture has already resolved its values. See G6-01 for the fixture itself.
   - The new `ContainerImageParityTests` case (no `WithBindMount`, no `docker.sock` in the fixture source) meets G4-17-18. `WithRealm` copies the file into the container, so there is no bind mount.
   - The parity test's own `FROM` regex is looser than `sandbox.py`'s `IMAGE_FROM_RE`. G6 checked the Keycloak line against `IMAGE_FROM_RE` by inspection, and it matches: repo `quay.io/keycloak/keycloak`, tag `26.7.4`, a 64-hex digest, alias `keycloak`.
