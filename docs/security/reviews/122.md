## Rulings asked for

1. **The log-once slot is claimed by the 429 writer: accepted.** The framework calls `AttemptAcquire` and then `AcquireAsync` for one request, so claiming the slot at acquire time would be wrong. The writer runs once per refused request, the slot lives on the refusing partition (`PartitionLimiter.cs:143-156`), and the counter still counts every refusal. The log fields still come from the closed lists, and the enrichment scope is disposed (`RateLimitResponses.cs:101-105`).
2. **Unmapped `/api` and `/bff` paths are in the `api` class: accepted.** This fails closed: no new or unmapped server path is unlimited. The cost is the T122-07 class: one cookie authentication per request, which reaches Redis only for a cookie that unprotects, bounded by the `api` budget. The SPA fallback, `/assets` and the health endpoints stay unclassified, which is unchanged scope.
3. **`Retry-After` is always `ceil(window / segments)`: accepted.** It is the earliest moment any permit can come back. A client that spent its whole budget in one segment may meet a second 429, and that is acceptable for a hint: the SPA never retries on its own (`bff.ts`), and the window bounds the lockout. It reveals only the segment size, which T122-08 already accepts.
4. **The raised Development limits: accepted.** `appsettings.Development.json` loads only in the Development environment. The stack forces `Production` and refuses any value that names Development (`stackguards.py:807, 815`). The values are within the validator's maximum. The limiter tests set their own limits explicitly.
5. **The devops additions.**
   - **`keyring reset --confirm --all-keys`: accepted.** It uses the same argv builder (exact-argv test), the same refusal before any change, `--confirm`, and stops the BFF first. It deletes only regular `*.xml` files inside the one volume and prints counts. It is needed: a key wrapped by a leaked certificate passes the strict rule, so the plain reset keeps it.
   - **The shell plaintext rule is stricter than the BFF's (substring, case-insensitive): accepted.** That direction is fail-safe. Every file the BFF rejects as plaintext, the shell also rejects. A false positive costs one forced sign-in and never keeps a plaintext key. The shell does not check the root element or where `decryptorType` sits, so a hand-crafted file could pass `verify` and still fail the BFF. That is detective only, the BFF then fails closed, and the only writer who could craft it is R-1.
   - **`add` refuses if any of the four files exists: accepted, and correct.** It never overwrites what may be the only copy of a wrapping key, and it never merges into a half-written set.
   - **`reset` leaves the BFF stopped: accepted, and safer.** The BFF comes back only through `up`, which runs `prepare` first and `verify` after.
6. **The spike note, `rsa-1_5` key transport inside `EncryptedXml`: acceptable for a key ring at rest.** The attacks on PKCS#1 v1.5 (Bleichenbacher) and on unauthenticated CBC (padding oracle) both need an adaptive decryption oracle. Here the BFF unwraps only key XML read from its own volume, at start-up and at the periodic refresh. No network caller can submit a ciphertext. The only feedback is "the BFF starts or does not". Getting it needs write access to the volume and control over restarts, which is R-1, and anyone in R-1 can already read the PFX and its password from `/run/secrets`. Integrity was never this layer's job: the certificate is public (G2, T122-12). It is a compliance exception, recorded as B-02.
7. **`KeyRingStartupCheck`'s `keyring.startup_check` Activity with no tags: accepted.** The span name is a constant and the span carries no attribute, so no path, key id or certificate data is exported. Its only effect is a trace id on the event 1830 line (V16.2 correlation). Not setting an error status when the check throws is cosmetic.
8. **`EagerConfigurationGuard` and the `Bff__DataProtection__*` variables: no leakage risk.** The test assembly disables parallelization (`AssemblyInfo.cs:9`, `ParallelMode.None`), and the guard holds a static lock. It sets the variables, forces the host to build, and clears them in `finally`. The values are random certificates generated per run (`KeyRingTestSupport.cs:28-38`), not secrets. Process environment variables die with the test process and are never persisted. One harmless side effect: a variable already set in the developer's shell would be cleared for that process. No finding.
9. **S-122-05 (two-phase one-shot): backlog, not fix-now** (B-01). The residual is contained to the one volume and the one-shot's own read-only root. The fix is more than a few lines, and it needs Linux and BusyBox proof that this host cannot give.
