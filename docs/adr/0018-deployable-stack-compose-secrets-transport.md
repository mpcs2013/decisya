# 0018. Deployable stack: Compose from `aspire publish` plus a reviewed overlay, file secrets, single-host internal transport

- Status: Accepted (Marco, 2026-10-05, #120 G2)
- Date: 2026-10-05
- Deciders: Marco
- Tags: hosting, security

## Context and problem statement

Issue #120 makes the stack deployable: Caddy, Keycloak, Postgres, Redis, the Api, the BFF (with the SPA), the migrator and an OpenTelemetry collector, on one Linux Docker host (the NAS in #132; a local Linux host for #120's proof). ADR-0001 and ADR-0007 say the Compose file comes from Aspire's Docker Compose publishing. ADR-0016 fixes the hosting boundary: networks, R9 isolation, Caddy's internal CA. ADR-0017 publishes the signed release images.

Four questions are still open, and each is a security or hosting decision:
1. Where does the Compose file come from, and how does a reviewer see what will run?
2. Where do secrets live, and how are they rotated (system baseline C-20)?
3. Is traffic between containers on the same host encrypted (C-11)?
4. Which accounts own the database (C-06)?

Forces:
- **Security:** the box is shared with personal data (ADR-0016 R9). A secret in an environment variable shows in `docker inspect`, in Container Manager's UI and in crash dumps.
- **Reviewability:** guard tests need a static file. An output generated only at deploy time cannot be reviewed in a PR.
- **Aspire's publisher** knows the app wiring (environment names, endpoints, dependencies). Its object model may not cover every hardening key, and its typed integrations wire secret parameters into environment variables.
- **Solo-developer time and the J3455 CPU:** every certificate and secret is Marco's to rotate. TLS on every internal hop costs CPU and adds a CA.
- **Portability:** the same files must run on the go-live VPS with configuration changes only (ADR-0016).

## Decision drivers

- What runs is exactly what was reviewed and scanned.
- No secret value in source, in an image, in a Compose `environment:` entry, in `.env`, or on a command line.
- No home-network address in the repository.
- Fail closed: a missing variable, secret or trust root stops the start.

## Considered options

### Compose source

1. **Two committed files: `deploy/compose/docker-compose.yaml` generated by `aspire publish` from a publish-mode model in the AppHost (app wiring), plus a hand-written overlay `deploy/compose/docker-compose.stack.yaml` (isolation and security). CI regenerates the first file and fails on drift. The guards test the merged effective configuration** (chosen).
2. **`aspire publish` at deploy time only, nothing committed.** Rejected: nothing to review or guard before it runs.
3. **One hand-written Compose file, no `aspire publish`.** Rejected: it contradicts ADR-0001, ADR-0007 and the issue's Done-when, and the environment names drift from the app model. It is the fallback if Aspire 13.5's publisher cannot meet the constraints in the outcome. That fallback needs Marco's decision, because it changes the Done-when.
4. **Everything in the AppHost through `PublishAsDockerComposeService` and `ConfigureComposeFile`.** Rejected as the rule: if the object model lacks a key (`pids_limit`, `!reset`, `secrets` targets), the hardening would be split between two places with no clear owner.

### Secret store (C-20)

1. **Compose file secrets: one file per credential in `<stack>/secrets/` (directory 0700, outside any Git working tree), mounted read-only under `/run/secrets/`. .NET reads them with the key-per-file configuration source. Images that read only environment variables get a read-only entrypoint wrapper that exports the value inside the container just before `exec`** (chosen).
2. **Environment variables from `.env`.** Rejected: values show in `docker inspect` and the Container Manager UI, and `.env` is one `git add -f` from the repository.
3. **A secret manager (Vault, OpenBao, Infisical, a cloud KMS).** Rejected for Phase 0: one more service to run, unseal, back up and patch on an 8 GB box, and its unseal key still sits on the same host. Review at go-live.
4. **Docker Swarm secrets.** Rejected: Swarm mode is not used, and it brings an encrypted Raft store for a single node with no gain.

### Internal transport (C-11)

1. **No TLS between containers on the single host's internal bridge networks. TLS wherever a hop passes Caddy. Per-hop network segmentation, authentication on every store, `NET_RAW` dropped everywhere** (chosen).
2. **TLS on every hop** (Postgres `verify-full`, Redis TLS, Kestrel HTTPS). Rejected for one host. It needs a second CA or exported leaf keys and per-service rotation, and it protects only against an attacker who already has root on the host or raw-socket access on the bridge. R9 removes that access, and host root can read process memory anyway. ADR-0016 also makes Caddy the only TLS terminator.
3. **The BFF calls the Api over plain HTTP.** Rejected: it reverses the #19 control (G4-19-01, `Bff:Api:Address` must be `https` outside Development). The BFF reaches the Api through Caddy instead (D5 in the architecture note).

### Database ownership (C-06)

1. **A bootstrap init script (superuser, first init only) creates `decisya_migrator` (LOGIN, NOSUPERUSER, CREATEROLE, NOCREATEDB, NOINHERIT, NOREPLICATION, NOBYPASSRLS) and the `decisya` database it owns. It revokes PUBLIC `CONNECT` on every database. The migrator creates the per-module roles itself, so on Postgres 16 and later it holds ADMIN OPTION only on the roles it created** (chosen).
2. **The migrator keeps the superuser.** Rejected: that is C-06.
3. **The init script creates every module role, and the migrator only grants.** Rejected: every new module would need an init-script change on an already-initialised volume, and the migrator would still need CREATEROLE to set passwords.

## Decision outcome

Chosen options: Compose 1, secrets 1, transport 1, ownership 1.

1. **Compose.**
   - Ownership is split by key. The generated file owns services, images, non-secret environment, dependencies and healthchecks. The overlay owns networks, aliases, fixed addresses, published ports, `secrets:`, `configs:`, volumes and bind mounts, users, `cap_drop`, `security_opt`, `read_only`, limits and logging.
   - The generated file contains none of the overlay's keys, and no secret parameter exists in the publish-mode model.
   - Release images appear only as `${DECISYA_API_IMAGE}`, `${DECISYA_BFF_IMAGE}` and `${DECISYA_MIGRATOR_IMAGE}`. Their values come from the release's `images.txt`, after `cosign verify`.
   - Third-party images appear as literal `tag@sha256` references from `ContainerImages.cs`.
   - `aspire publish` must not build or push images. If Aspire 13.5 cannot meet these constraints, G4 stops and Marco decides on option 3.
2. **Secrets.** As in option 1. Connection-string secrets are derived by the stack tool from the same generated credential that the database side uses, so one generator owns each credential and its rotation. The secret list and the rotation procedures are in `docs/architecture/deployable-stack.md`.
3. **Transport.** As in option 1. **Review trigger:** any hop that leaves a single host (the VPS with a managed database, K3s, a second node, or telemetry exported off-box) gets TLS with verification on that hop, decided before the move.
4. **Ownership.** As in option 1.
5. **Amendments.**
   - **ADR-0015 §2:** the scan targets are the aliases built from `ContainerImages.cs`, now `postgres`, `keycloak`, `redis`, `caddy` and `otelcollector`, still failing closed on anything else.
   - **ADR-0016 R9.6:** the back-channel network holds Caddy, the BFF and the Api only. Caddy and Keycloak share a separate `internal: true` network (#124 review B-6).

### Consequences

- Good:
  - Reviewers and guards see the exact effective configuration. The app wiring stays generated from the AppHost model.
  - No secret value appears in `docker inspect`, the Compose files, `.env` or an image. Rotation is a file swap plus a documented restart.
  - The migrator is not a superuser, and PUBLIC cannot connect to any database.
  - No second CA, no internal certificates to rotate. Caddy stays the only TLS terminator.
- Bad:
  - Two Compose files, and a drift check that fails every third-party digest bump until `aspire publish` is re-run and the output committed.
  - Internal hops are plaintext. This is acceptable only while everything runs on one host with R9 in force (review trigger above).
  - Secret files are readable by the container processes that mount them (mode 0444 inside a 0700 directory, unless G4 proves Compose applies per-file `uid` and `mode`).
  - The Keycloak entrypoint wrapper puts its database and bootstrap passwords into the Keycloak process environment (not into the container configuration).
  - The BFF-to-Api hop adds a Caddy hop on the J3455 (measured by F3).
- Enforced by:
  - the drift check (CI);
  - the guard tests over the merged `docker compose config` output and over `caddy adapt` output (`deploy/tests/`);
  - `stackctl.py check` before every deploy;
  - the Testcontainers role test (C-06);
  - the trust integration test (B-3);
  - the clean-clone stack smoke on a Linux Docker host (all listed in the architecture note).
