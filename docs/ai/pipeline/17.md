**Title:** feat(identity): Keycloak realm export, bff client and seeded users (0.05)

Adds Keycloak as the identity provider for local development (ADR-0002):
- the `decisya` realm with the `decisya-bff` client and dev users;
- Keycloak's own Postgres database;
- a Testcontainers realm-configuration suite.

Documents:

**Realm** (`deploy/keycloak/decisya-realm.json`; hand-written, no key material):
- `decisya-bff`: confidential, PKCE S256 required, standard flow only, one exact redirect URI (`https://localhost:7200/signin-oidc`).
- Tokens: access token lifetime 300 s, RS256 only, signed request objects only, refresh tokens rotated.
- `tenant_id`: an admin-only user-profile attribute, mapped into the access and ID tokens. A user cannot change their own tenant; a test proves it.
- Claims: an audience mapper adds `decisya-api`. Roles: `tenant-user` and `platform-admin`.
- Dev users `dev-alice` and `dev-bob` (two tenants) and `dev-admin` (`platform-admin`, no tenant), all `@decisya.test`.
- The `admin-cli` password grant is refused.
- Secrets are `${DECISYA_BFF_CLIENT_SECRET}` and `${DECISYA_DEV_USER_PASSWORD}` placeholders. Keycloak 26.7.4 does not substitute `${env.X}`, and it silently keeps an unset `${X}` as the literal value. So the AppHost refuses to start without the variables, and tests pin both behaviours.

**AppHost:**
- Postgres 18 and Keycloak 26.7.4, pinned by digest (`ContainerImages.cs`, with a parity test against the sandbox image list).
- Keycloak's own least-privilege role and database are created by an init script. It passes the password with psql `\getenv` and turns statement logging off.
- The BFF client secret and database password are generated on first run. The dev password is set once by Marco in the local secret store (GETTING-STARTED §3).
- Postgres and Keycloak are persistent containers with fixed names (`decisya-postgres`, `decisya-keycloak`), so a hard AppHost stop can't leave a second Postgres writing the same volume. That incident happened once and corrupted the dev volume.
- AppHost tests use a throwaway volume and ephemeral containers, and the AppHost refuses ephemeral mode on the dev volume.
- Locally the issuer is `https://localhost:8080/realms/decisya`: Aspire terminates HTTPS for containers when the dev certificate is trusted. #18 and #20 take the URL from the endpoint.
- All ports listen on 127.0.0.1 only, verified with the AppHost running and after it stops.

**Tests** (`tests/Decisya.Identity.Tests`):
- Realm-file, secret-rule, init-script and image-parity checks run in the unit step.
- 30 `Category=Integration` Testcontainers tests cover the realm settings, the mappers, browser-style logins, the negative flows (PKCE, redirects, grants), a tenant self-edit attempt, reimport, and placeholder regressions. They use a test-only cookie relay, because .NET's CookieContainer drops Keycloak's Secure cookies over http.
- CI's Integration step now runs them, with masked throwaway secrets generated in that step only, and no longer tolerates zero tests.
- `KeycloakResourceTests` is skipped for #70 (Aspire test-host TLS on the auto-HTTPS management port). The Done-when was verified live on the real AppHost.
