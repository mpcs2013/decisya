## G7 PR body draft

**Modules.Entitlements: plans, features, overrides and trials (0.11)**

Closes #23

**Summary.** This PR adds the entitlement check every later feature gates on, and the platform pattern for admin commands that act on another tenant (ADR-0012).
- **`Decisya.Modules.Entitlements.Contracts`:** `IEntitlementService.IsEnabledAsync(FeatureKey)` checks the current tenant only; `FeatureKey` (`module.feature`); `FeatureKeys.LedgerTransactions` and `ForecastingScenarios`.
- **Plans in code (`PlanCatalog`):**
  - Free has `ledger.transactions`; Pro adds `forecasting.scenarios`, the Phase 3 feature.
  - Every tenant is on Free implicitly; nothing is written at sign-in, and Entitlements stays independent of Tenancy.
- **Schema `entitlements`:** `TrialGrant` (one per tenant, ever) and `FeatureOverride` (one per tenant and feature, reason required, optional expiry). Both are tenant-scoped.
- **Evaluation:**
  - precedence: an unexpired override, then an active trial (Pro, 14 days), then the plan;
  - expiry is computed with `IClock` at read time and is end-exclusive;
  - it fails closed: an unknown or default key, no tenant or an invalid tenant is denied before any query, and a database error propagates, never allowing (NFR-35).
- **Admin commands** (start trial, grant override, revoke override) are internal `[AllowCrossTenant]` handlers under **ADR-0012 (Accepted)**:
  - a caller with a tenant or an invalid claim gets `Forbidden` before any database access;
  - each handler opens its own context fixed to the target tenant, so the #22 filter and write guard enforce "this tenant only", unchanged;
  - there is no HTTP path until #24 audits them and #25 adds the admin endpoint (conditions recorded on #24, #25 and #26).
- **Rules:**
  - `TenantResolution.For`, `FromClaim` and `NoTenant` join `CrossTenantQueryRule`'s list, so only `[AllowCrossTenant]` types may create a tenant scope in the modules;
  - in `Decisya.Api`, only `CallerContextMiddleware` may.
- **Least privilege:**
  - the migrator creates a second role, `decisya_entitlements` (DML on its own tables only), from a client-side SCRAM verifier;
  - the AppHost gives the API exactly two connection strings, `tenancy` and `entitlements`, each for its own role;
  - a cross-schema test proves neither role can read the other module's schema. #21 had deferred this test.
- **Override reason:** marked `[Sensitive]`; it never appears in logs, errors or metric tags (tested with a marker).
