## G7 PR body draft

feat(messaging): tenant safety before the first wolverine use (c-13, c-14)

**Summary**

Closes register findings C-13 and C-14 before the first Ledger feature (D-012 point 2).
- **Envelope tenant at both ends.**
  - **Sending:** `EnvelopeTenantStamp` is the scope's `IMessageBus`. It stamps the sender's tenant and caller on every send and overwrites forged values. With no tenant, it throws.
  - **Receiving:** `EnvelopeTenantMiddleware` accepts only the exact canonical tenant text and a valid caller id. Otherwise it refuses as `missing`, `malformed` or `no-caller`. A message never grants admin or MFA.
  - Wolverine runs in-process only: `MediatorOnly`, a null message store, System.Text.Json only, explicit handler lists, no `[AllowCrossTenant]` handler, and `TypeLoadMode.Static`.
- **One key builder:** `TenantKey` (`tenant:seg` / `tenant/seg`). Enforced by R10 and R11, and by a two-tenant Redis test.
- **Outbox decision recorded:** ADR-0024 (Accepted, amendments 1 and 2). No Wolverine envelope entity goes in any EF model. The durable outbox gets its own issue when first needed (#243 item 231-1).
- **WolverineFx 6.39.1 behaviour pinned by tests:**
  - only invoke works under `MediatorOnly`;
  - handler dependencies are constructed before the middleware. This is fail-closed: `TenantDbContext` reads the tenant at use time, and R16 bans tenant or caller reads in constructors;
  - a nested invoke loses the caller id and is refused as `no-caller`. Fixing it is a hard prerequisite in #243 item 231-5;
  - Wolverine's four chain-less handlers are listed exactly and blocked by R17.
- **Architecture rules R1–R17** in `Decisya.ArchitectureTests`, each with red and green fixtures.

**Packages** (CLAUDE.md package rule, G6 S-08):
- `WolverineFx` 6.39.1 (already pinned): first use, in `Decisya.Api` only. It is an in-process mediator (`MediatorOnly`) with the envelope-tenant pipeline (ADR-0024).
- `WolverineFx.RuntimeCompilation` 6.39.1 (new reference, Marco approved 2026-11-01): `tests/Decisya.Api.Tests` only, so the messaging tests run real handler chains. It brings Roslyn (`Microsoft.CodeAnalysis.*` 5.0.0), `JasperFx.RuntimeCompiler` 5.0.0, `System.Composition.*` 9.0.0 and `Humanizer.Core` 2.14.1 into that test project only. R15 keeps it out of `src`.
- Code generators in the Api graph: `JasperFx.SourceGenerator` 2.73.2 (a build-time analyzer) and `FastExpressionCompiler` 5.4.1 (a runtime expression compiler used by JasperFx). No runtime C# compiler runs in the Api (`TypeLoadMode.Static`).
- New serializers: none. Only System.Text.Json is registered, besides Wolverine's two intrinsic entries, which are inert in-process. `Spectre.Console` enters the Api graph as a JasperFx dependency, but `RunJasperFxCommands` is never called.
- `Polly.Core` moves 8.4.2 → 8.6.5 in the Api graph, transitively through JasperFx.

**Rollback:** revert the PR. No schema, data, volume or configuration step is involved: no migration, no stored messages, no new environment variable.
