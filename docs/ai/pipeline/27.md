## G4 evidence (the B-01 fix only)

**B-01:** the BFF passed a browser-chosen `traceparent`, `tracestate` and `baggage` through to the Api and Keycloak (Medium; #15 T-20/F-4, never picked up by #19). There were two causes:
- ASP.NET Core hosting extracted inbound context through `DistributedContextPropagator`.
- OpenTelemetry's AspNetCore instrumentation re-extracted it through the global `Propagators.DefaultTextMapPropagator` (trace context plus baggage) and re-parented the BFF's server span to the browser's trace.

YARP also copied those headers.

**identity-dev (src/Decisya.Bff):**
- `Proxy/BffTracePropagator.cs`: extracts nothing and injects W3C. It's registered in DI for the BFF only, never as `DistributedContextPropagator.Current`.
- `ProxyConfiguration`: YARP removes `traceparent`, `tracestate`, `baggage`, `Request-Id` and `Correlation-Context`.
- `Program.cs` calls `builder.UseInboundTraceRoots()`.
- `TraceContextIsolationTests` (Integration, a canary trace id and baggage):
  - the BFF span is a new root, and the Api gets a BFF-rooted `traceparent` with no baggage or canary (so outbound injection still works);
  - every request of the login flow is a new root, and the Keycloak backchannel carries only the BFF's context.
  - Red first: the canary trace id was adopted.

**backend-dev (src/Decisya.ServiceDefaults):** the opt-in `UseInboundTraceRoots<TBuilder>()` calls `Sdk.SetDefaultTextMapPropagator(new TraceContextPropagator())`. It's process-wide, documented, and called by the BFF only, so the Api keeps normal propagation. `InboundTraceRootsTests` (non-parallel; the original propagator is restored) cover the extension and that `AddServiceDefaults()` alone keeps the default composite.
