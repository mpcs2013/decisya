### Part 1, identity-dev spike (2026-10-08; tests in `tests/Decisya.Bff.Tests/Spike/`, throwaway)
- **R1 FAIL:** a rejected `SlidingWindowRateLimiter` lease carries no `RetryAfter` value; `FixedWindowRateLimiter` does. The G2 D6 fallback `ceil(window / segments)`, clamped to 1 through `WindowSeconds`, is the **only** path.
- **R2 PASS:** in the chain, the second lease is the one refused, the first is released, and window permits are not returned (the admin double count holds).
- **R3 PASS:** a wrapper deriving from `ReplenishingRateLimiter` that forwards `TryReplenish` and `IdleDuration` recovers after the window under the real heartbeat; a plain wrapper never recovers. 50 idle partitions are evicted (idle limit about 10 s).
  - **Finding:** the wrapper must override `DisposeAsyncCore`, because eviction calls `DisposeAsync`, whose base does nothing.
- **R4 PASS:** no `TimeProvider` hook exists, so tests use a short real window.
- **R5 PASS:** the cookie authentication result is cached per request (one `RetrieveAsync`).
- **D1 PASS on Windows and in the pinned chiseled Linux image** (read-only, `cap-drop ALL`, no network): the RSA 4096 PFX round trip works from base64 plus a password, and rotation (B with A previous) works.
  - **Note for G6:** the framework wraps with `rsa-1_5` key transport inside `EncryptedXml`, its built-in choice.
- **D2 PASS:** `IKeyManager.GetAllKeys()` doesn't throw; `key.Descriptor` throws `CryptographicException` for an undecryptable key, and the check is read-only.
- **D3 PASS:** `StartingAsync` runs before `DataProtectionHostedService` creates a key. A fail-closed check blocks start and writes no new key; without the check, a second key is silently created.
- **D4 PASS:** key files are 0600 by default, so the D9 fallback isn't needed; only top-level `*.xml` is read.
- **D5 PASS:** `NullXmlEncryptor` writes `encryptedSecret` around a clear `unencryptedKey/masterKey`. G3's strict rule is needed and sufficient.

## G7 PR body draft

### Summary
Abuse and key protection for the BFF (C-09a, C-05). Phase 0, synthetic users only (ADR-0016).

- **Rate limiting (C-09a):** ASP.NET Core's built-in limiter in the BFF, before authentication, so the OIDC callback is covered too.
  - Four route classes, each per 60 s:
    - login: 10 per client address;
    - back-channel logout: 300 per client address (raised from 30, because Keycloak doesn't retry a refused logout; checked on 26.7.5);
    - api: 300 per session, or 60 per address when anonymous;
    - admin: 30 per session, also counted in api.
  - Partitions:
    - a domain-separated session HMAC, never the cookie;
    - otherwise the address seen after the trusted forwarded headers, with IPv6 grouped by /64;
    - a trusted proxy's own address counts as `unknown`, a shared bucket, never "no limit".
  - The 429 is a generic ProblemDetails with `Retry-After`. `ratelimit.rejected` (event 1820) is logged once per partition per window, plus the counter `decisya.bff.ratelimit.rejected`.
  - Development has raised limits.
  - Caddy is unchanged: stock Caddy already overwrites `X-Forwarded-For` and passes the 429 through. New guards and a smoke check prove it.
  - The edge limiter itself (C-09b) stays a go-live item.
- **The key ring (C-05):**
  - encrypted with `ProtectKeysWithCertificate` (RSA 4096, a base64 PFX plus a password in four BFF-only file secrets), with the current and previous certificates for rotation and a 90-day key lifetime;
  - a fail-closed start-up check outside Development: 0700 directory, every live key decrypts, strict plaintext detection, no weak certificate. It runs in its own trace;
  - the BFF image gains `--generate-keyring-certificate` (no network, password on stdin);
  - `stackctl` gets:
    - `secrets add`, `rotate` and `retire` for the certificate;
    - `keyring prepare` (owner 1654, 0700/0600, which settles #120's writability item);
    - `keyring reset --confirm`, which deletes plaintext keys;
    - `--all-keys` for a compromise;
    - a read-only `verify`.
  - The certificate is not backed up (Marco keeps a copy off the NAS). The backup contract and the compromise and lost-certificate procedures are in the runbook.
- **SPA:** a 429 from `/api` or `/bff/me` shows "Too many requests. Please wait a moment and try again." instead of reading as signed out, with no automatic retry.
- **Go-live gate:** C-09 is split into C-09a (closed here) and C-09b (open, blocks public exposure, covers the id host). C-05 closes after this PR and #30's restore drill. C-09a doesn't stop password guessing, which goes straight to Keycloak.

### Upgrading an existing #120 stack
Its key ring is unencrypted. Run `stackctl secrets add dataprotection_cert`, then `stackctl keyring reset --confirm`, then `stackctl up`. Everyone signs in once more. No stack has been deployed yet (#132).

### Rollback
Revert this PR. A stack that already ran this version has a certificate-encrypted ring: after the revert the BFF writes plaintext keys again, so run `keyring reset --confirm --all-keys` from this version first, or accept one forced sign-in. The dev environment needs no step.
