## Checks the architect asked for

- **The four `BASE_EXEC_FILES` paths are pinned exactly.** `ContractConstantTests.test_the_executable_allow_list_is_the_four_distroless_files` compares the tuple with the four literal paths, in order. `FileCheckTests` uses the same four in its good view and refuses an extra executable, a missing base file and a base file that lost its exec bit. `LayerViewTests.test_red_a_whiteout_of_a_base_file_is_seen` covers a whiteout. Pass.
- **The exact `SSL_CERT_FILE` value is pinned.** `ContractConstantTests.test_the_env_allow_list_is_exact` asserts `BASE_ENV == {"SSL_CERT_FILE": "/etc/ssl/certs/ca-certificates.crt"}` and the four-key allow-list. `ConfigCheckTests.test_red_another_ssl_cert_file_value_is_refused` and `test_red_a_missing_ssl_cert_file_is_refused` refuse another value and an absent key; `test_red_an_extra_env_key_is_refused` and `test_red_a_changed_xdg_value_is_refused` bound the rest. The Dockerfile side (`DockerfileInputTests.test_red_a_wrong_or_extra_runtime_env_is_refused`) keeps `SSL_CERT_FILE` out of the Dockerfile's own `ENV`, since it comes from the base. Pass.
- **BusyBox at `/usr/bin/busybox` (merged-usr).** `FileCheckTests` builds its view with `usr/bin/busybox` and the links in `usr/bin` pointing at `busybox`, and refuses a missing binary, a setuid binary and a link to something else. `LayerViewTests.test_the_merged_usr_names_resolve_to_one_path` shows that `/bin/...` and `usr/bin/...` names resolve to one path. The G4 container proof records `/bin -> usr/bin` in the real image. Pass. One note: the Dockerfile copies to `/bin/`, so the path is right only because the distroless base is merged-usr; the layer-view test and the real-image check cover that dependency, but nothing offline fails if a future base drops merged-usr (the build-job `inspect` would).

## Gaps, none blocking PR-1

1. **No offline pin of the workflow's #119 build-integrity lines** (M-2 c): `ref: ${{ github.sha }}` for each checkout and `RELEASE_SHA`, the sparse-checkout list, the single artifact name `caddy-image`, and login after download. `workflow_problems` has no rule for them, so a later edit could drop them without a red test. They are present in the file today and the first real run exercises them. Recommendation: add rules and red cases in a follow-up (small, same file), or record as accepted until PR-2.
2. **The Dockerfile's version-binding `RUN` block** (M-1 f) has no red test that it stays. It self-checks at build time, so it is not silent when it fails, only when it is deleted.
3. **`go` line not below Caddy's** (M-1 d) is compared by hand against upstream data (G4 evidence), not by a test.
4. Real-run proofs still to come after the first CI run of `caddy-image.yml`: gitleaks canary and per-layer scan, the three negative verify cases, the binary SHA-256 against the host build `c2dbd858bcdbddc7405b7ab8bbda8d0b90fbbdc9997e86bfb5576cf66fa03c8c` (G3 S-2). The pre-push results are what Marco reads before making the package public.
5. PR-2 items (pin switch, M-3, M-2 e, ADR-0014 pointer, `ContainerImageParityTests`, `test_stackctl.py`, smoke on a Linux host) are pending and need their own G5 pass.
