# Phase 0 – Generated agent/skill roster, stale-roster check, and a `Docs:` line in G7

## Issue #76 — docs(ai): generated roster diagram, stale-roster check and Docs line in G7

### Scope note (role framing)

This issue has no tenant-facing capability at all: it fixes the Claude Code tooling
that went stale after #74 split the implementer agents (`docs/ai/README.md` still
said "9 agents / 13 skills" with the old lanes, and nothing caught it). Every story
below is written from the vantage point of the two people who actually read or rely
on this doc and this check, exactly as the issue names them:

- **"As Marco"** (the Decisya platform operator and solo developer) for stories about
  what the generated docs must show him and how he adds an agent or a skill.
- **"As the orchestrator session"** for stories about a machine-enforced gate: the
  main Claude Code session is the one that runs `roster.py --check`, reads its
  failure message, and is the one `gates.py` blocks at G7.

**Entitlement plan: N/A for every story in this issue.** `docs/ai/README.md`,
`.claude/scripts/roster.py`, `.claude/boundaries.json` and `.claude/scripts/gates.py`
are contributor-facing tooling, not a tenant-facing module. No subscription plan
gates any of it, and no `module.feature` entitlement key applies — the same reasoning
`docs/requirements/phase-0/keycloak-realm.md` gave for #17's identity infrastructure
stories.

**Scope, tightly bound to issue #76 (per the manifest):**

- A generated block in `docs/ai/README.md`, rendered by `.claude/scripts/roster.py`
  from `.claude/boundaries.json`, each agent's frontmatter in `.claude/agents/*.md`,
  the skills each agent names, and the G4 path-routing table: two Mermaid diagrams
  (gates → agents, with G4's path routing and G3/G6 marked as the security-reviewer
  gates; agents → skills) plus a generated roster table.
- Moving the per-agent Docker allow-list (today `DOCKER_ALLOW` in
  `.claude/hooks/agent_boundaries.py`) into `.claude/boundaries.json` as the single
  source, with `lint.py` validating it.
- `roster.py --check`, wired into the pre-commit `claude-lint` hook and CI's
  `claude-config` job, failing when the doc is stale.
- `gates.py`'s G7 check requiring a `Docs:` line (files touched, or `none: <reason>`)
  for new manifests, without breaking any manifest that already passed G7.
- A doc-ownership statement in `docs/ai/README.md` (main session owns `docs/ai/**`;
  tech-writer owns runbooks/onboarding; no required PR review or CODEOWNERS, one
  human).

**Out of scope, with the owning issue (unchanged from the manifest):** a PR template;
rewriting any historical manifest, security review or ADR to add a `Docs:` line or
otherwise conform to the new format.

### Story 1 — The roster part of `docs/ai/README.md` is generated, not hand-maintained

As Marco, I want the agent table, the skill table and two Mermaid diagrams in
`docs/ai/README.md` generated by `.claude/scripts/roster.py` from
`.claude/boundaries.json`, each agent's frontmatter, the skills it names, and the G4
routing table, so that the roster I read always matches the live configuration
instead of the hand-edited snapshot that went stale after #74 (9 agents / 13 skills,
the pre-split lanes).

#### Acceptance criteria

```gherkin
Feature: The roster block in docs/ai/README.md is generated from the live config

  Scenario: The generated table lists exactly the current agents
    Given every agent file under .claude/agents/*.md and .claude/boundaries.json as
      they exist on disk
    When python .claude/scripts/roster.py renders the generated block
    Then the roster table lists exactly the agents that have a .claude/agents/*.md
      file, each row showing its model, its gate(s), its write lane (from
      boundaries.json), the skills it names and its tools beyond Read/Grep/Glob
    And no agent present on disk is missing from the table, and no row names an
      agent that has no .claude/agents/*.md file

  Scenario: The gates-to-agents diagram shows G4's path routing and marks G3/G6
    Given the gate table (G0-G7) and the G4 path-routing table (paths to
      backend-dev/platform-dev/identity-dev/frontend-dev)
    When roster.py renders the Mermaid gates-to-agents diagram
    Then every implementer that G4 can route to appears as a node reachable from G4,
      distinctly from one another
    And the G3 and G6 nodes are visually distinguished from the other gate nodes
      (e.g. a distinct Mermaid class) as the security-reviewer gates

  Scenario: The agents-to-skills diagram links only the skills an agent actually names
    Given each agent's declared skills, the same list the generated table's "Skills"
      column shows
    When roster.py renders the Mermaid agents-to-skills diagram
    Then each agent node links only to the skill nodes it names
    And every skill under .claude/skills/*/SKILL.md that no agent names is either
      omitted or shown unlinked, never attached to an agent that does not name it

  Scenario: The generated block replaces only its own content
    Given docs/ai/README.md has hand-written sections outside the generated block
      (the pipeline explanation, the guardrails table, "Starting an interaction")
    When roster.py renders the generated block
    Then only the generated block's content changes
    And every hand-written section is byte-for-byte unchanged
```

### Story 2 — Regenerating the roster twice in a row changes nothing

As Marco, I want `roster.py` to be idempotent and deterministic, so that running it
after an unrelated commit never produces a spurious diff, and two contributors (or
two CI runs) generating the same config get byte-identical output.

#### Acceptance criteria

```gherkin
Feature: roster.py is idempotent

  Scenario: A second run with no config change produces no diff
    Given roster.py has just regenerated the block in docs/ai/README.md once
    When python .claude/scripts/roster.py runs again, with no change to
      .claude/boundaries.json, .claude/agents/*.md or .claude/skills/*/SKILL.md
    Then docs/ai/README.md is byte-for-byte identical to its state after the first
      run (git diff reports zero changed lines)

  Scenario: Output does not depend on filesystem or clock state
    Given the same .claude/boundaries.json, agents and skills content
    When roster.py renders the block twice, with the agent and skill files listed in
      a different filesystem enumeration order and at two different wall-clock times
    Then both renders produce identical output (agents and skills are sorted by a
      stable key, e.g. name; no timestamp or run-specific value is embedded)
```

### Story 3 — `roster.py --check` catches a stale roster before it merges

As the orchestrator session, I want `python .claude/scripts/roster.py --check` to
fail, naming the exact command to run, whenever an agent, a lane, a tool, a skill or
a Docker allow-list entry changed without the doc being regenerated, and I want that
check wired into the pre-commit `claude-lint` hook and CI's `claude-config` job, so
that a stale roster (exactly #76's own trigger) can never reach `main` again.

#### Acceptance criteria

```gherkin
Feature: roster.py --check fails a stale roster and says how to fix it

  Scenario: The check passes when the doc matches the current config
    Given docs/ai/README.md's generated block was produced by the current
      .claude/boundaries.json, .claude/agents/*.md and .claude/skills/*/SKILL.md
    When python .claude/scripts/roster.py --check runs
    Then it exits 0 and reports no drift

  Scenario: Adding or changing an agent without regenerating fails the check
    Given a new file is added under .claude/agents/, or an existing agent's
      frontmatter (model, gate, tools) changes, and docs/ai/README.md is not
      regenerated afterwards
    When python .claude/scripts/roster.py --check runs
    Then it exits non-zero
    And its message names the exact command to run to fix it
      (python .claude/scripts/roster.py, with no flags)

  Scenario: Changing a lane, a skill or the Docker allow-list without regenerating
    fails the check
    Given any one of: an agent's write lane in .claude/boundaries.json changes; a
      skill is added, removed or renamed under .claude/skills/; the Docker allow-list
      entry for an agent changes — and docs/ai/README.md is not regenerated
      afterwards
    When python .claude/scripts/roster.py --check runs
    Then it exits non-zero and names the regenerate command, the same as the
      previous scenario

  Scenario: The check is proven red before it is proven green
    Given a test fixture that reverts docs/ai/README.md's generated block to a stale
      snapshot while leaving the current .claude/agents, boundaries.json and skills
      in place
    When the .claude test suite's roster tests run against that fixture
    Then at least one test asserts --check exits non-zero against the stale
      snapshot (red), and a second asserts it exits 0 once roster.py has regenerated
      the block from the same fixture (green)

  Scenario: pre-commit blocks a commit that leaves the roster stale
    Given a commit stages a change under .claude/agents/**, .claude/boundaries.json
      or .claude/skills/**, without a matching regeneration of docs/ai/README.md
    When the pre-commit claude-lint hook runs
    Then it fails, and its output includes roster.py --check's failure message

  Scenario: CI blocks a PR that leaves the roster stale
    Given a pull request's diff changes .claude/agents/**, .claude/boundaries.json
      or .claude/skills/**, without a matching regeneration of docs/ai/README.md
    When the claude-config job in .github/workflows/ci.yml runs
    Then the job fails on the roster.py --check step, with the same failure message
      a local run would show
```

### Story 4 — The Docker allow-list lives in `boundaries.json`, not in the hook

As Marco, I want the per-agent Docker allow-list (today `DOCKER_ALLOW` inside
`.claude/hooks/agent_boundaries.py`) to live in `.claude/boundaries.json` instead, so
that `roster.py` can render it from the one file that already describes every other
per-agent permission, and so that a Docker allow-list change is caught by the same
lint and the same stale-roster check as any other lane change.

#### Acceptance criteria

```gherkin
Feature: boundaries.json is the single source for the Docker allow-list

  Scenario: The Docker allow-list is readable from boundaries.json
    Given .claude/boundaries.json
    When it is parsed
    Then it carries, for platform-dev and devops, the same Docker subcommands each
      may run today (platform-dev: ps/container ls, logs without -f, port, volume
      ls; devops: ps, logs without -f, compose up/ps/logs without -f, compose down
      without -v/--volumes/--rmi), and no Docker entry for any other agent

  Scenario: Docker enforcement is unchanged after the move
    Given the existing must-allow and must-deny Docker command fixtures the .claude
      test suite already carries (platform-dev's ps/logs/port/volume ls allowed,
      inspect/exec/cp/run denied for every agent, devops's compose down -v denied,
      every shell-syntax bypass case)
    When agent_boundaries.py's decide_docker reads the allow-list from
      boundaries.json instead of its own DOCKER_ALLOW dict
    Then every one of those existing fixtures still passes, unchanged

  Scenario: lint validates the new key
    Given boundaries.json's schema validation
    When a Docker allow-list entry is malformed, or names an agent that has no entry
      under "agents", or an unlisted agent's Docker entry is present
    Then python .claude/scripts/lint.py reports the problem and exits 1

  Scenario: The generated table shows the Docker allow-list
    Given boundaries.json's Docker allow-list
    When roster.py renders the generated agent table
    Then platform-dev's and devops's rows show their allowed Docker subcommands, and
      every other agent's row shows none
```

## Implementation notes for G2 (non-blocking)

None of these change a story's observable behaviour or its Gherkin, so none is left
as an open question — they are mechanism choices for the architecture note, recorded
here so G2 does not have to re-derive them:

1. **Where the `Docs:` line lives, and how `gates.py` recognizes a "new" manifest**
   (Story 5). The line belongs inside the "## G7 PR body draft" section — the
   existing G7 artifact per the issue skill ("manifest § G7 PR body draft") — not a
   new column on the gate table. "New" is best decided by template shape, not a
   date: once this issue updates `gates.py init()`'s template to include a `Docs:`
   placeholder, a manifest either has that section (checked, per Story 5's
   scenarios) or predates the change and has no `Docs:`-prefixed line to check
   (unaffected, per Story 5's fourth scenario). This avoids a hardcoded cutoff date,
   which would misfire on a manifest edited after the cutoff or created from a stale
   local checkout.
2. **Mermaid styling for "G3/G6 marked as security-reviewer gates"** (Story 1). A
   `classDef` applied to the G3 and G6 nodes (GitHub's Mermaid renderer supports
   `classDef`/`class`) is the simplest option that needs no extra tooling. Story 1's
   acceptance criteria say "visually distinguished," not which mechanism, so this
   choice cannot fail the criteria.
3. **Shape of the Docker allow-list inside `boundaries.json`** (Story 4). Add a new
   top-level `docker` key, sibling to `deny` and `agents`, mapping agent name to its
   allow-list — rather than changing `agents.<name>` from a plain glob list to an
   object. That keeps every existing write-lane entry and `agent_boundaries.py`'s
   `decide_write` unchanged, and needs no migration for agents with no Docker entry.
   This is a schema change to `_hooklib.validate_boundaries` either way, so G3
   should review it as part of the lane-change review rule (`gates.py`'s
   `REVIEW_REQUIRED_PATHS`), same as #74.
